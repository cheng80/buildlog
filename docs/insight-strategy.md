## 1. 한 문장 요약

빌드로그는 **이미 만든 화면·영상·링크 하나를 프로젝트에 붙여 올리고, 새 게시물을 피드에서 발견하며 프로젝트 타임라인에 개발 기록을 쌓는 서비스**다. 차별점 후보는 **붙여넣기 하나로 게시 / 유튜브·Shorts devlog 링크 게시 / 정직한 공식 콘텐츠**다. 재노출은 기본 제공 가치(기본 기능)로 설명하며 Q4·BR-004·경쟁 비교 카피 금지는 유지한다. 외부 소개 문구도 새 게시·프로젝트 타임라인의 실제 동작 중심으로 쓴다. [확정, 사용자 2026-09-26] (D1·Q21). 결정의 관찰 근거는 [경쟁 관찰 §3](research/competitor-check.md)에 있으며 사용 편의·수요의 동등함을 입증하지 않는다([공식 안내](https://disquiet.io/announcement), [프로젝트 기록](https://disquiet.io/products/zerolaunch), 확인 2026-09-26 22:39 / 22:42 KST).

## 2. 핵심 인사이트

### I-1. 게시물 하나가 네 곳에서 쓰인다 [인사이트]

핸드오프 §4.2의 핵심 가치 4개(쉽게 기록 / 지속 노출 / 프로젝트 중심 / 홍보 자동화)는 전부 "글 하나 → 피드 + 프로젝트 타임라인 + 공유 카드 + 포트폴리오"라는 한 구조에서 나온다. 원칙은 "개발자가 콘텐츠를 새로 만들게 하지 말고, 이미 만들고 있는 것을 가져오게 한다"이다. 이는 콘텐츠 공급 전략이며, 게시 마찰을 줄이는 모든 결정(유형 선택 없음, 내용 하나 이상이면 게시, URL 붙여넣기 자동 판별, 유튜브 링크만으로 게시)이 여기서 파생된다.

### I-2. 출시는 한 번의 행사가 아니라 계속 이어지는 과정이다 [인사이트]

기존 런칭 서비스는 "완성 → Launch → 며칠 노출 → 종료"다. 빌드로그는 "아이디어 → 개발 게시물 → 재노출 → Beta → Release → 재노출 → 업데이트 → 재노출"이다. 재노출 규칙은 단순하다. 최신순 피드에서 새 공개 게시물이나 Release가 프로젝트를 다시 앞으로 끌어낸다(BR-004). 편집·좋아요는 시각을 갱신하지 않는다. 핸드오프는 국내 유사 서비스(디스콰이엇 메이커로그, GeekNews Show GN 등)가 있어 제품 등록·개발로그만으로는 차별화가 약하다고 판단했고, 제품 명세는 "국내 유일" 같은 경쟁 우위 주장을 카피에서 금지했다. 재노출은 **기본 제공 가치(기본 기능)**로 설명하며 경쟁 우위를 주장하지 않는다. [확정, 사용자 2026-09-26] (Q21)

K-4 보강: [경쟁 관찰](research/competitor-check.md)의 공개 화면·공식 안내를 근거로 S-2 기본 기능 재분류를 확정했다. [확정, 사용자 2026-09-26] 확인 URL·시각은 보고서 §2·§3(2026-09-26 22:39~22:42 KST)에 있으며 사용 편의·수요의 동등함을 입증하지 않는다.

### I-3. 초기 사용자 부족을 제품 구조로 흡수했다 [인사이트]

사용자 원문: "활성화율이 높지 않고 게시물이 적어도 정적으로 죽어가는 느낌이 들어서는 안 된다." 이 한 문장이 공식 카드 3종, 데모 프로젝트 3개, 메인 5:1 혼합(Q14), 하루 1회 수집·초안 5개·게시 2개(Q8), 자체 BuildLog 프로젝트의 실제 개발 게시를 낳았다. 공식 카드는 "튜토리얼처럼 유저 피드를 대신"하는 역할이며 광고 반복이 아니라 실제 콘텐츠여야 한다.

### I-4. 정직성이 반복되는 제약이자 브랜드 자산이다 [인사이트]

가짜 반응 수·후기·가격 금지(BR-006), 데모 명시, 출처·날짜 보존(BR-011), 광고 구분(BR-013), 카드 반응 숫자 숨김(Q3), 인기순은 데이터 준비 후, 결제 성공 URL을 완료로 표시하지 않음. 이 제약은 문서 전반에 열 번 이상 등장한다. 초기 사용자가 적을 때 숫자를 숨기는 결정은 방어이면서 동시에 "작아도 정직한 곳"이라는 포지셔닝이 된다.

### I-5. 관심은 개발자가 아니라 프로젝트에 붙는다 [인사이트]

게시물은 프로젝트 하나에 귀속(ADR-0001), 팔로우 대상은 프로젝트(ADR-0003), 소유는 한 계정, 팀명은 소개 정보. 소셜 그래프의 노드가 사람이 아니라 **만들고 있는 것**이다. 이는 팔로잉 피드가 곧 재노출 채널이 되게 하고, 개발자가 여러 프로젝트를 가져도 관심이 분산되지 않게 한다. 또한 "개발과 무관한 게시물" 필터가 프로젝트 필수 연결 하나로 자연스럽게 생긴다.

### I-6. 과제 조건은 핵심 루프 밖에 격리했다 [인사이트]

지도는 프로필의 시·군·구 대표 좌표만(Q11), 결제는 Featured 한 상품·테스트 1,000원·수동 시작(Q12). 사용자 원문 "지도 위치 기능은 개발사 주소와 소개 페이지 정보에 붙이는 정도로", "예약은 작업량·예외가 많아 안 하고 싶다". 즉 과제 6조건(회원·CRUD·지도·결제·취소·내역)을 충족하되 게시→재노출 루프를 잠식하지 않게 최소 침습으로 설계했다.

### I-7. 자동화는 SNS를 큐레이션 미디어로 확장한다 [인사이트]

Q5에서 사용자는 권장안보다 범위를 넓혀 외부 RSS·AI 원고를 MVP에 넣고, 인디 뉴스·포럼 중심에 주요 업계 뉴스까지 요구했다. 수집 경로 확인이 끝난 소스는 GeekNews, Show HN, itch.io devlogs, Ars Technica다. 공식 카드는 **비제작자(2차 타깃: 새 앱·게임을 찾는 사람)에게 제공할 볼거리**이기도 하다. 반복 방문 효과는 검증되지 않았으므로 기대 역할은 S-6의 피드 채움 보조로 둔다. [제안, K-5] 단, GPT 모델·월 예산은 미정이며 상한 미설정 시 유료 생성을 실행하지 않는다. 초기 허용 소스는 위 4개로 확정했고 Ars Technica는 업계 뉴스 용도로만 사용한다. [확정, 사용자 2026-09-26] (Q15)

### I-8. 한국 개발자 문화에 맞춘 진입점 [인사이트]

한국어 우선, 한국 개발자 태그(앱인토스, Flutter, Expo, Supabase, 카카오API, 네이버API), Kakao 지도, Toss 결제, GeekNews 소스. 사용자 원문 "요즘은 유튜브 영상로그를 만드는 사람도 많아서" → 유튜브·Shorts 링크만으로 게시물이 되는 것이 특정 집단(영상 devlog 제작자)을 향한 명확한 훅이다.

### I-9. 시각이 주인공이다 [인사이트]

사용자 원문 "재미와 눈으로 보이는 부분이 풍성한 것". 피드 미디어 1:1 프레임, 크림색 바탕에 화면(이미지)이 주인공, 첨부 4개·40MB, GIF 동작 미리보기. 텍스트만 게시도 허용하지만 기본 경험은 스크린샷 한 장이다.

### I-10. 40일은 상한이고 순서는 자유다 [인사이트]

일차별 배정은 폐기됐다. 완료는 구현·검증 증거로만 판단한다. 따라서 전략은 "무엇을 먼저 검증하면 나머지 리스크가 가장 줄어드는가"로 짜야 하고, 달력 순서로 짜면 안 된다.

### I-11. 확정은 전부 제품 규칙이고, 미정은 전부 자원이다 [인사이트]

PLAN-001의 기존 16개 답변은 제품 동작·정책과 실행 조건을 다룬다. 허용 소스·광고 정책·데모 프로젝트·운영자 권한을 제품 결정으로 분리한 뒤 Q15~Q24 권장안을 채택했다. [확정, 사용자 2026-09-26] (K-14). 이미 답한 Q1~Q14 원문을 바꾸거나 재질문하지 않으며 [PLAN-001 §9 확정 답변](plans/PLAN-001-planning-review.md#9-3차-문답-q15q24-2026-09-26-확정)을 구현 기준으로 사용한다. 가용 시간·GPT 모델·월 예산·도메인과 7일 수집 후 형식 판단은 남아 있다. 도구·계정·키·스케줄러는 확정 정책을 만족하도록 구현 시 선택·검증한다.

제목의 "미정은 전부 자원"은 K-14가 반박한 기존 해석을 식별하기 위해 보존했다.

### I-12. 출시 시점의 운영자·개발자·첫 제작자는 같은 사람이다 [인사이트]

제품 명세 §3은 역할 4개(인디 개발자, 팀, 방문자, 운영자)를 두지만, 핸드오프의 사용자 배경과 Q7 미정은 1인 개발을 시사한다(K-3). 사용자 본인 계정에 명시적 운영자 역할을 부여한다 [확정, 사용자 2026-09-26] (Q18). 초기에는 한 사람이 개발, 하루 검수(Q8), BuildLog 자체 devlog 연재, 데모 유지, 신고·결제 오류 확인을 함께 맡는다. 관리자 화면과 파이프라인의 편의 기능은 그 한 사람의 시간에서 나온다. 로드맵의 축소 원칙(소스 수 → 카드 템플릿 → 관리자 편의)이 이 인사이트와 정확히 일치한다. 자체 devlog는 콘텐츠이면서 서비스의 첫 실사용 검증이므로, S-3의 "가장 싼 확인"이 곧 운영 지속 가능성 확인이다.

### I-13. 발견 신호는 전부 게시 행위의 파생값이다 [인사이트]

기술 명세 §4에서 `last_activity_at`은 최신 공개 게시물의 `published_at`에서 계산하고, 프로젝트 현재 버전은 최신 유효 Release에서 파생한다. 편집은 `updated_at`만 바꾸고, 피드 커서는 `(published_at, id)`다. 사용자가 순위에 직접 손댈 수 있는 필드가 없다. 재노출(BR-004)은 별도 랭킹 로직이 아니라 "새 게시 = 새 `published_at`" 하나로 구현되며, 게시 빈도에 따른 피드 집중은 429만으로 충분히 방어된다고 단정하지 않는다. 같은 프로젝트의 연속 카드 접기를 표시 규칙으로 함께 적용한다 [확정, 사용자 2026-09-26] (K-12). S-2의 "설명 없이 체감"이 가능한 구조적 이유다. 활동 점수·개인화(핸드오프 §4.6)를 나중에 넣더라도 이 파생 규칙 위에 얹어야 하며, 파생값을 수동 필드로 바꾸는 순간 정직성(I-4)도 함께 깨진다.

### I-14. 정직성은 문구가 아니라 타입과 상태로 구현된다 [인사이트]

피드 응답은 `user_post | official_card | promoted_project` 세 타입으로 구별되고(기술 §6), 주문·결제·노출은 상태 기계 3개로 분리되며 `confirming`·`reconciliation_required`가 정식 상태다(기술 §4). 소식 카드는 `source_items`에서 파생되지만 사용자 게시물·프로필·프로젝트로 변환되지 않고, 데모는 `is_demo`로 집계에서 제외된다. I-4의 규칙(BR-005/006/011/013)은 카피 지침이 아니라 데이터 구조로 강제된다. 따라서 정직성 위반은 카피 검수가 아니라 타입 추가·상태 병합을 시도하는 코드 변경에서 먼저 드러난다. S-4의 검수 기준 "규칙 위반 0건"은 이 구조 덕에 코드 리뷰 항목으로 내려갈 수 있다.

### I-15. 팔로잉 탭이 유일한 재방문 경로다 [인사이트]

Q3으로 댓글·알림함이 빠지고, Q14로 팔로잉 피드에는 프로젝트 게시물만 남는다. 방문자가 "다음 게시물"을 보는 경로는 팔로잉 탭 자발 재방문 하나이며, 제작자가 반응을 확인하는 경로는 Q19의 본인 통계로 제공한다 [확정, 사용자 2026-09-26]; K-1 결정 의존성은 해소됐다. 이는 팔로잉 피드 열람 계측의 공백과 별개다. 행동 이벤트 5개(기술 §8)에는 팔로잉 피드 열람이 없어 제품 명세 §2의 지표 `프로젝트 팔로우 → 다음 게시물 열람`은 현재 정의로 측정할 수 없다. 기술 §8의 측정 범위 [미정]이 이미 이 공백을 인정하고 있다. S-8이 이 공백을 다룬다.

## 3. 핵심 전략 가설

### S-1. 첫 게시까지의 마찰을 서비스의 제1 지표로 삼는다 [가정]

- **가설**: 프로젝트 생성 → 첫 게시 전환이 유지율을 결정한다. 붙여넣기 하나(이미지 또는 URL)로 게시가 끝나야 한다.
- **근거**: I-1, I-8, I-9. 제품 명세 §2가 이미 `프로젝트 생성 → 첫 게시`를 관찰 지표로 제안했다.
- **실행 방향**: 온보딩 3단계(프로젝트 만들기 → 오늘 만든 것 올리기 → 링크 공유)를 한 흐름으로 잇고, 프로젝트 생성 직후 화면에 게시 입력창을 둔다(SCREEN-003의 "오늘 만든 것을 올려 보세요"). 프로젝트가 없을 때 게시 입력을 잃지 않게 한다(SCREEN-004).
- **검증**: 프로젝트 생성 후 첫 게시 도달 비율, 첫 게시까지 클릭 수. 첨부 유형 비율(이미지 / 유튜브 링크 / GitHub / 텍스트만)로 I-8의 유튜브 훅 가설을 함께 본다.
- **가입 지표 [제안]**: S-3에서 분리한 가입 관련 검증은 가입 → 프로젝트 생성 → 첫 게시 흐름에서 본다. 가입·클릭 수·첨부 유형의 기록 방식은 최소 이벤트 5개와 별도로 정한다. [미정]
- **리스크**: 너무 가벼운 게시가 저품질 글을 낳는다. 방어는 프로젝트 필수 연결(I-5)과 신고·숨김이며, 활동 점수 도입은 데이터 후로 미룬다.
- **K-1 결정 반영 [확정, 사용자 2026-09-26]**: 첫 게시의 마찰 감소만으로 두 번째 게시를 설명할 수 없다. FR-007에서 본인 게시물·본인 프로젝트의 좋아요 수·저장 수·프로젝트 팔로우 수를 본인만 보는 화면에 제공하기로 확정했다(Q19). K-1 결정 의존성은 해소됐으며 실제 후속 게시 효과는 출시 후 검증한다.
- **K-1 대체 확인 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: 공개 프로젝트의 후속 게시 유무·게시 간격과 공개 반응/외부 링크를 `docs/research/creator-loop-observation.md`에서 기록한다. 동기와 본인 통계의 효과는 공개 관찰만으로 확정하지 않는다. 제공 여부·범위는 사용자 결정(Q19)이며 효과 검증과 구분한다.

### S-2. 재노출 규칙은 단순하게 유지하고 "설명 없이 체감"시킨다 [가정]

- **가설**: 최신순 + 새 게시 재노출이라는 단순 규칙이 이해하기 쉽고 스팸 유인이 낮다. 활동 점수·개인화 비율은 초기 데이터 없이는 임의 순위가 된다.
- **기본 기능 [확정]**: 재노출은 기본 제공 가치로 재분류한다 [확정, 사용자 2026-09-26] (D1·Q21). 한 문장 요약의 차별점 후보에서 재노출을 빼고 실제 게시·프로젝트 타임라인 동작으로 소개한다. Q4·BR-004·경쟁 비교 카피 금지는 유지한다. [경쟁 관찰 §3](research/competitor-check.md)의 확인 근거·시각은 §1에 연결했다.
- **근거**: I-2, I-13, Q4 확정. 핸드오프의 70/30 개인화·활동 점수·주 2회 Boost는 채택되지 않았다.
- **실행 방향**: 프로젝트 페이지의 타임라인과 탐색의 "최근 업데이트순"이 재노출을 시각적으로 보여준다. 카피에서 경쟁 서비스 비교나 "국내 유일"은 쓰지 않는다. 순위에 영향을 주는 값은 모두 게시 행위의 파생값으로 유지한다(I-13).
- **검증**: `게시 → 프로젝트 페이지 열람`, `프로젝트 팔로우 → 다음 게시물 열람`(제품 명세 §2). 한 프로젝트의 게시 간격 분포로 "연재"가 실제로 일어나는지 본다. 후자는 S-8의 열람 이벤트 없이는 측정할 수 없다. [미정]
- **리스크와 대응**: 게시 폭주로 피드가 한 프로젝트에 집중될 수 있어 전체·팔로잉 자연 피드에서 같은 프로젝트 게시물이 연속 2건 이상이면 최신 1장과 “이 프로젝트의 이전 게시물 N개 펼치기”를 표시한다. 펼치면 원래 위치·최신순 그대로 보이고 접힌 Release가 있으면 “Release 포함”을 표시한다. 공식 카드·광고는 제외하며 Q4 정렬·`published_at`·타임라인 전체 기록은 유지한다. [확정, 사용자 2026-09-26] (D2·K-12). 한 페이지 응답 안에서만 접는 방식은 [확정 원칙 / 기본값은 제안, 구현 시 변경 가능] [기본값 제안]이다. [허구 목업 §4](research/competitor-check.md)는 설계 참고이며 실제 이용량·429 통과 증거가 아니다(로컬 검토 2026-09-26 23:07:58 KST). 이후 인기·점수는 실제 데이터로 필요성을 확인한 뒤 추가한다(FR-008).

### S-3. 실사용자 0명에서도 "살아 있는 피드"를 운영 콘텐츠로 만든다 [가정]

- **가설 [제안, K-7]**: 공식 카드·데모 프로젝트·BuildLog 자체 개발 게시의 역할은 비회원 이탈 방지·사용 방법 안내다. 특히 BuildLog 자체 개발 게시가 실제 사용 예시가 되는지 확인한다. 가입 유도 효과를 전제하지 않는다.
- **재방문 원인 가설 [제안, K-9]**: 볼거리와 사용 예시가 있어 자발적으로 피드를 다시 여는 습관 방문이 생길 수 있다. 반복 방문 효과는 미검증이며 S-8의 새 글 구분선과 구분해 관찰한다.
- **근거**: I-3, I-4, I-12, FR-009. 핸드오프 우선순위는 Build Prompt ★5, Project Spotlight ★5(외부 의존 없음), 개발 Tip ★5.
- **실행 방향**: 외부 의존 없는 카드(만들기 주제·이번 주 프로젝트·자체 devlog)를 먼저 채우고, 외부 RSS·AI 카드는 상한 안에서 보충한다. 공식 카드가 광고처럼 보이지 않게 실제 정보를 담는다. 5:1 혼합 상한을 지켜 피드가 공식 카드로 덮이지 않게 한다.
- **검증 [제안]**: 비회원 피드 체류·두 번째 페이지 이동, 공식 카드 클릭(게시하기 버튼·원문 읽기). 가입은 S-1·S-5 지표에서 본다. 데모·운영자 활동은 실제 사용자 지표에서 제외하고 별도 집계한다. 체류·이동·가입·공식 카드 클릭의 추가 기록 방식은 [미정]이며 최소 이벤트 5개만으로 측정됐다고 표시하지 않는다.
- **리스크**: 운영자 하루 검수 부담. 운영자는 곧 개발자 본인이므로(I-12) 하루 게시 2개 상한이 현실적 천장이며, 소스 수·템플릿 수부터 줄이는 조정 원칙(ROADMAP)을 따른다.
- **가장 싼 확인 [제안, K-7]**: 소개 사이트 저장소나 Markdown에 BuildLog 개발 게시물을 2주간 주 2회 작성해 운영 지속 가능성을 확인한다. 기간·횟수는 실험 설계용 제안이다. 지속하기 어렵다면 데모 프로젝트·만들기 주제 공식 카드 중심의 운영안을 검토한다.

### S-4. 정직성을 브랜드 원칙으로 승격한다 [가정]

- **가설**: 숫자 숨김·데모 표시·출처 보존·광고 구분을 일관되게 지키면 초기 소규모 커뮤니티에서 신뢰가 성장 자산이 된다. 인스타그램식 방향(사용자 원문)을 따르되 인스타그램식 지표 경쟁은 따르지 않는다.
- **근거**: I-4, I-14. BR-005/006/011/013, Q3.
- **실행 방향**: 카드에는 숫자 대신 실제 행동 상태(내가 좋아요·저장·팔로우했는지)를 보여준다. 공식 카드에는 "공식", 데모에는 "데모", 유료 노출에는 "광고"를 제목 근처에 붙인다. 미리보기 실패·결제 확인 중 같은 불확실 상태를 그대로 표시한다. 피드의 정직성 규칙(I-14)을 자동 검사 3개로 지킨다. ① 피드 타입별 배지(공식/데모/광고) 존재 ② 기본 카드에 반응 숫자 없음 ③ `promoted_project`가 자연 피드 커서 결과에 없음. [확정, 사용자 2026-09-27; KR3·K-13·1차 완료 조건] 결제 상태 분리는 기술 명세의 상태 전이 검증을 따른다. 타입 병합·파생값의 수동 필드화는 정직성 규칙 위반으로 본다.
- **검증**: 정량 지표보다 규칙 위반 0건을 검수 기준으로 둔다. 실제 수치 공개 요구가 생기면 "실제 값만, 데모 제외"로 대응하며 가짜 수치는 어떤 경우에도 넣지 않는다.
- **리스크와 결정(K-1)**: 숫자가 없어 “반응 없음”처럼 보일 수 있어 본인 게시물·본인 프로젝트의 좋아요 수·저장 수·프로젝트 팔로우 수를 본인만 보는 프로젝트 관리·게시물 상세·프로필에 제공한다 [확정, 사용자 2026-09-26] (D7·Q19). 기본 카드 숫자 숨김(Q3)·가짜 반응 금지·댓글/알림함 이후 범위를 유지한다. 제공 결정으로 K-1 의존성은 해소됐으나 보상 루프의 실제 효과는 검증 전이다.
- **K-1 대체 확인 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: 공개 반응이 보이는 프로젝트와 후속 게시의 동반 여부를 기록하되 인과로 해석하지 않는다. 본인 통계는 Q19 확정 범위로 구현하며 공개 관찰을 효과의 증거로 확대하지 않는다.

### S-5. 프로젝트 공개 URL을 초기 성장 채널로 본다 [가정]

- **가설**: 초기 유입은 제작자가 자기 프로젝트 링크를 외부(SNS, 유튜브 설명란, GitHub README)에 공유하며 생긴다. 프로젝트 페이지가 곧 포트폴리오이므로 링크 하나의 품질이 전환을 좌우한다.
- **근거**: I-1, I-5, 소개 사이트 약속 "이 페이지 링크 하나로 프로젝트 전체를 소개할 수 있다", 온보딩 3단계의 "링크 공유".
- **실행 방향**: 안정적인 ID 경로(이름 변경에 영향 없음), 공개 상태를 확인하는 OG 메타, 공유 버튼을 프로젝트·게시물 상세에 둔다. SNS용 공유 이미지 자동 생성은 이후 범위로 유지한다.
- **검증**: 프로젝트 페이지의 외부 referrer 비율, 공유 버튼 사용, 비회원의 프로젝트 → 피드 이동.
- **가입 지표 [미정]**: S-1의 가입 후 프로젝트 생성·첫 게시 흐름과 S-5의 외부 공유 유입 후 가입을 함께 확인하는 안을 둔다. 가입·referrer·페이지 이동의 추가 기록 방식은 최소 이벤트 5개와 별도로 정하며, 불필요한 개인 연결이나 전체 referrer URL 저장을 전제하지 않는다. [제안]
- **리스크**: 숨긴 콘텐츠의 외부 캐시 잔존. 기술 명세 §6의 운영 제한으로 기록하고 자체 제공 종료와 구분한다.
- **K-6 확인 [제안]**: K-1 인터뷰에 프로젝트 페이지를 README에 넣을지와 이유를 포함한다. 5명 중 3명 이상이 넣지 않겠다고 답하면 S-5를 성장 채널에서 제외하고 유입 가설을 다시 세우는 안을 검토한다. 인원·임계값은 실험 설계용 제안이며 현재 조사 결과가 아니다.

### S-7. Featured 테스트 결제는 과제 조건 충족과 결제 파이프라인 기술 검증으로 다룬다 [제안]

### S-8. 팔로잉 탭을 재방문 채널로 설계하고 열람을 측정한다 [가정]

- **재방문 원인 가설 [제안, K-9]**: S-5의 제작자 외부 공유 링크 또는 S-3의 습관 방문이 다시 피드를 여는 계기가 될 수 있다. 원인은 아직 검증되지 않았고 새 글 구분선 자체를 방문 계기로 보지 않는다.
- **재방문 보상 가설 [제안, K-9]**: 돌아온 사람이 팔로잉 탭에서 "마지막 열람 이후 새 게시물"을 구분하면 다음 게시물을 찾기 쉬워질 수 있다. 새 글 구분선은 재방문의 보상이며 알림함(Q3 제외)을 추가하는 결정이 아니다.
- **근거**: I-5, I-15, Q3·Q14 확정, 제품 명세 §2 지표 `프로젝트 팔로우 → 다음 게시물 열람`, SCREEN-001의 팔로잉 탭.
- **실행 방향 [제안]**: 팔로잉 탭을 한 번의 이동으로 도달하게 두고, 마지막 열람 시각 이후의 새 게시물 구분선이나 건수를 표시하는 안을 검토한다. 이는 카드 반응 숫자가 아니라 본인의 열람 상태이므로 Q3과 충돌하지 않는다. 팔로잉 탭이 비면 공식 카드로 채우지 않고 탐색으로 연결한다(Q14, SCREEN-001). 마지막 열람 시각의 저장 위치는 구현 시 정한다. 행동 이벤트의 비회원 세션은 가입 계정·다른 기기에 연결하지 않고 집계는 운영자 역할에 한정한다 [확정, 사용자 2026-09-26] (Q20). 본인 통계는 Q19 확정 범위를 따르며 열람 계측과 구분한다.
- **검증 [제안]**: 팔로잉 피드 열람 이벤트(예: `following_feed_viewed`)를 K-2 도구 결정과 함께 추가할지 검토한다. 팔로잉 탭 열람 시 마지막 열람 이후 새 글 N>0 여부를 함께 기록 [제안]. 현재 이벤트 5개만으로는 이 가설을 측정할 수 없다. 행동 이벤트의 30일 후 삭제/익명화(Q13 상수 재사용 [확정 원칙 / 기본값은 제안, 구현 시 변경 가능] [기본값 제안])는 확정 정책이다 [확정, 사용자 2026-09-26] (D8·Q20). 측정 가능해지면 `project_followed` 이후 같은 사용자의 팔로잉 피드 열람과 팔로우한 프로젝트의 `post_published` 발생을 잇는다. `팔로우 시각 < 게시 시각 < 열람 시각`을 만족해도 N>0은 새 글의 존재를 뜻할 뿐 개별 게시물 실제 열람의 증거가 아니며, 이를 확인할 기록은 별도 정의한다. [미정]
- **리스크 [제안]**: 알림 없는 자발 재방문은 낮을 수 있다. 외부 링크 유입과 반복 피드 열람을 구분해 관찰하고, 확인된 요구가 Q3·ADR-0003과 충돌하면 재검토 사유를 사용자에게 올린다. 이 가설만으로 알림함을 MVP에 넣지 않는다.

## 6. 확정된 정책과 남은 미정

## 7. 다음 행동 제안

[전략 레드팀 §5](strategy-red-team.md#5-이번-주-할-일)의 여섯 항목을 [PLAN-001 후속 확인 표](plans/PLAN-001-planning-review.md#8-레드팀-후속-확인-항목2026-09-26)에서 추적한다. PRD의 A1~A5는 [확정, 사용자 2026-09-27]이며 그 밖의 관찰·실험 제안은 구분한다. 현재 답변 대기 질문은 없다. **PRD 확정 → 1차 프로토타입 착수 준비**로 진행하며 [K-10 사용자 실행 체크리스트](research/oauth-login-check.md)를 먼저 연결한다.

1. 공개 관찰 기록 완료: [보고서](research/creator-loop-observation.md)의 한계를 유지하고 확정된 본인 통계(Q19)를 구현·검증에 연결한다. 동기·공유 의향·지불 의사·실제 재방문은 미확인이고 인터뷰는 사용자 결정으로 불가하다. [제안]
2. 행동 이벤트 구현 준비(K-2): 자체 `events`·`pg_cron` 30일 정리·서버 발급 HttpOnly 쿠키 30분 절대 만료·SQL 뷰 1개와 관리자 페이지 1개를 확정했다 [확정, 사용자 2026-09-27]. [기술 §8](03_TECH_SPEC.md#행동-이벤트)에 따라 KR5 이벤트 5개를 1차에 검증하고 Q20 완전 준수는 실제 정리·권한·백업 검사 뒤 판정한다. K-9 추가 열람 계측은 2차 후속이다.
3. 로그인 확인과 소요 측정 준비(K-3·K-10): 사용자가 [K-10 체크리스트](research/oauth-login-check.md)를 실행해 두 제공자 결과를 기록한 뒤 핵심 흐름 1 이슈와 시작 시각을 준비한다. 현재 로그인 결과는 미기록이다. 하루 2시간·총 예산 상한 80시간, 실제 투입 27시간 초과 시 재협상과 소스 수 → 카드 템플릿 수 → 관리자 편의 기능의 축소 후보 순서를 적용한다 [확정, 사용자 2026-09-27].
4. K-4·K-12 결정 적용: 재노출 기본 기능과 연속 카드 접기는 [확정, 사용자 2026-09-26]이다. Q4 정렬·타임라인 보존, 펼치기·Release 안내·페이지 경계를 구현 시 검증한다.
5. 소스 4개 7일 수동 수집(K-5): 초기 허용 목록은 Q15 확정이며 [1일차](research/source-sample/2026-09-26.md) 이후 나머지 6일·중복 비교를 보완해 주간 다이제스트 형식만 후속 판단한다. [제안]
6. 확정 결정 구현 준비: [PRD](PRD-buildlog.md)와 [PLAN-001 채택 기록](plans/PLAN-001-planning-review.md#2026-09-27-prd-권고안-채택)의 A1~A5를 기존 Q1~Q24·D1~D11에 더해 적용한다. KR3 정직성 자동 검사 3개·KR5 이벤트 5개를 포함한 KR1~KR5를 1차 완료 기준으로 삼으며, 2·3차도 첫 버전 범위 안에서 준비한다 [확정, 사용자 2026-09-27]. 효과·수요·앱 검증은 별도 증거가 필요하다.
