# 빌드로그 개발 작업 흐름

갱신일: 2026-09-17 · 상태: **기획 단계의 작업 기준안**

## 1. 작업의 기준

이 저장소의 [AGENTS.md](../AGENTS.md)와 기존 [이슈 운영](agents/issue-tracker.md), [triage](agents/triage-labels.md), [도메인 문서](agents/domain.md) 규칙을 유지한다. ZIP에 포함된 지침으로 기존 파일을 덮어쓰지 않는다.

- 제품·UI·기술 명세는 만들려는 동작을, 현황 문서는 실제 구현·검증 상태를 설명한다.
- 불확실한 제품 결정은 [기획 보강 계획](plans/PLAN-001-planning-review.md)에 근거·권장안·영향을 남긴다.
- 문서 작성 요청으로 앱 생성·서비스 연결·배포까지 승인된 것으로 해석하지 않는다. 커밋·push·PR·merge·원격 변경은 사용자가 요청한 범위에서 수행한다.
- 기존 사용자 변경은 보존한다. 작업 시작 시 Git 상태와 현재 소스·지침을 확인한다.
- 40일은 최대 기간이다. 일차별 작업 할당이나 기능 진행 순서를 강제하지 않는다. 우선순위·준비 상태·실제 의존성에 따라 다음 작업을 선택하고, 독립 작업은 병렬 진행하거나 함께 완료할 수 있다.

## 2. 기획에서 개발로 넘어가는 조건

1. 확정된 단일 소유자·프로젝트 팔로우·최신순 피드·외부 수집/AI·Featured 테스트 결제와 첨부/취소 정책을 유지하고, 선택한 기능에 필요한 미정 상세만 정한다.
2. 화면별 ASCII에서 주요 이동과 빈/실패 상태를 확인한다.
3. 데이터·권한·외부 연동 제약을 검토하고 선행 결정을 반영한다.
4. 작업 목록과 현재 우선순위·의존성을 보고 당장 진행할 기능의 구현 명세와 이슈를 만든다. 로드맵의 나열 순서를 따를 필요는 없다.
5. 사용자가 구현을 요청하면 해당 범위에서 준비된 작업을 진행한다. 실제로 필요한 기반이 없다면 그 의존성을 함께 해결한다.

모든 사소한 문구를 미리 정해야 시작할 수 있다는 뜻은 아니다. 다만 소유권 모델·금전 처리·개인정보 공개처럼 후속 구조에 영향을 주는 결정은 의존 구현 전에 확정한다. 아직 미정인 가격으로 결제 상품을 만들지 않는다.

## 3. 작업 단위와 문서 위치

| 역할 | 위치 | 작성 시점 |
|---|---|---|
| 제품 정본 | `docs/01_PRODUCT_SPEC.md` | 사용자 동작/범위/규칙 변경 |
| 화면 정본 | `docs/02_UI_UX.md` | 화면 흐름/상태/문구 계약 변경 |
| 기술 정본 | `docs/03_TECH_SPEC.md` | 데이터/권한/API/인프라 변경 |
| 기능별 명세·이슈 | `.scratch/<feature-slug>/spec.md`, `issues/<NN>-<slug>.md` | 구체적인 구현 작업을 만들 때 |
| 복합 실행 계획 | `docs/plans/PLAN-xxx.md` | 여러 영역의 순서·의존성 설명이 필요할 때 |

구현 명세·이슈를 생성하거나 상태를 바꾸기 전 해당 운영 문서를 읽는다. 프로젝트 현황에 상세 이슈 내용을 중복 작성하지 않는다. 이번 단계에서는 기획만 작성하고 실제 구현 티켓을 미리 완료 처리하지 않는다.

## 4. 기능별 구현·검증 흐름

```text
완료 조건 확인 → 관련 명세·기존 코드 읽기 → 필요한 설계 보강
→ 작은 수직 기능 구현 → 적절한 검증 → 결과 확인·문제 수정
→ 정본·현황·인수인계 갱신
```

- 인증·권한 검사는 UI를 숨기는 것과 별개로 서버·DB 경계에 둔다.
- 스키마 변경은 migration으로 남기고 빈 DB 재현과 기존 데이터 영향을 확인한다. 운영 데이터 삭제를 개발 편의로 수행하지 않는다.
- 동시성·돈·공개 상태처럼 실패 비용이 큰 규칙부터 검증한다. 단순 문구 변경에 구현을 그대로 복제하는 테스트를 추가하지 않는다.
- 기능 변경으로 테스트가 실패하면 같은 승인 범위의 문제를 수정하고 다시 확인한다.
- 원인 조사·구현 중 발견한 범위 밖 작업은 현재 변경에 몰래 포함하지 않고 후속 이슈로 남긴다.

## 5. 실행·검증 명령의 상태

**현재 실행 가능한 앱 명령은 없다.** `package.json`, lockfile, 앱 코드가 생성되기 전까지 아래는 앱 기반 구성 시 갖출 스크립트 계약안이다. 이미 설치되거나 실행 성공한 명령이 아니다.

| 예정 명령 | 갖춰야 할 내용 |
|---|---|
| `pnpm install --frozen-lockfile` | 패키지 매니저·버전·lockfile 고정 후 재현 설치 |
| `pnpm dev` | 로컬 개발 서버 |
| `pnpm lint` | ESLint 검사. 선택 Next.js 버전에서 제거된 CLI를 가정하지 않음 |
| `pnpm typecheck` | TypeScript 검사 |
| `pnpm test` | 도메인·서비스 단위/통합 테스트 |
| `pnpm test:e2e` | 준비된 테스트 환경에서 주요 사용자 흐름 |
| `pnpm build` | 배포 빌드 |
| `pnpm start` | 빌드 산출물 실행 |

패키지 매니저는 pnpm 제안이며 기존 lockfile이 생기면 그 계약을 따른다. Supabase CLI 명령은 설치된 버전의 `--help`와 공식 문서를 확인하고 기록한다. 아직 존재하지 않는 seed·migration 스크립트를 재개 명령으로 안내하지 않는다.

## 6. 검증 시나리오

| 검증 묶음 | 실제 확인할 내용 |
|---|---|
| 문서 변경 | 상대 링크, ID 참조, 용어, 제안/확정 구분, 원본 누락, 실제 상태와의 일치 |
| 회원/프로젝트 | 신규 가입·재로그인·타인 수정 차단·프로젝트 CRUD·공개 URL |
| 게시/미디어 | 파일·영상·링크·일반 글, 중복 제출, 실패 입력 보존, 삭제 반영 |
| 피드/소셜 | 같은 게시물의 양쪽 노출, 페이지네이션, 저장 비공개, 팔로우 해제 |
| 관리자 | 승인 전 비노출, 예약 중복, 실패 재시도, 숨김·복원 |
| 외부 콘텐츠·AI | 인디 뉴스/포럼·업계 뉴스의 실제 수집, 출처·날짜 보존, 중복·스팸·개인 의견 구분, AI 구조/근거 검사·비용 제한·지시문 격리 |
| 위치 | 공개 수준·비공개 전환·정확 좌표 유출·지도 실패 대체 |
| 결제 | 정상 승인·취소·내역, 금액 변조, 중복/역순 사건, 결과 불명, 활성화/취소 경합 |
| UI | 360/390/768/1440px, 키보드·포커스·라벨, 로딩·빈·오류, 실제 대비 측정 |

완료된 검증을 이유 없이 반복하지 않는다. 변경·실패·미해결 위험이 있을 때 관련 범위를 다시 검사한다. 실제 제공자 연동은 mock 검증과 구분한다.

외부 RSS/API·AI 원고는 확정된 MVP 범위다. 내부 템플릿이나 mock만 통과하면 외부 자동화 검증은 `NOT_RUN` 또는 `INCOMPLETE`로 남긴다. 수집·생성·승인·게시의 단계별 입력/결과와 모델·프롬프트 버전을 기록한다.

## 7. 환경·배포·복구 제안

- 개발·미리보기·운영은 DB/키/리다이렉트 허용 주소/지도 도메인/결제 환경을 구분한다.
- 미리보기에서 실결제 키를 쓰지 않는다. 운영자 페이지와 작업 실행 URL도 인증한다.
- 배포 전: 명세의 관련 완료 조건, migration 적용 순서, 환경 설정, 빌드, 필수 E2E, 결제 상태 불일치 여부를 확인한다.
- 배포 후: 공개 읽기 → 로그인 → 안전한 테스트 데이터의 게시 → 미디어 → 작업 실행 상태를 점검한다. 실결제 검증은 별도 승인·운영 절차에 따른다.
- 복구: 앱 이전 버전으로 복귀 가능한 DB 변경을 우선한다. 데이터가 손실되는 역 migration을 자동 수행하지 않는다. 결제 불일치는 주문·제공자 상태를 대조한 후 복구한다.
- 백업/복원 가능 범위, 운영 연락 경로, 보존 기간은 실제 인프라 결정 후 적는다. 현재 준비되었다고 가정하지 않는다.

## 8. 완료 판정과 기록

- [ ] 요청한 범위가 구현됐다.
- [ ] 주요 성공·실패·권한·동시성 조건을 검증했다.
- [ ] 실패를 수정하거나 남은 한계를 명확히 기록했다.
- [ ] 제품·UI·기술 정본이 실제 계약과 일치한다.
- [ ] 현황·인수인계에 다음 작업과 검증 근거를 남겼다.

검증 결과는 `PASS / FAIL / INCOMPLETE / NOT_RUN / UNKNOWN`, 근거는 `RECHECKED / HISTORICAL / NONE`, 유효성은 `CURRENT / STALE / UNKNOWN`으로 구분한다. 날짜·리비전 또는 미커밋 산출물 식별·실행 범위·출처를 함께 기록한다. 문서 검사 PASS를 앱 빌드 PASS로 바꾸지 않는다.

커밋과 PR을 요청받으면 한국어 `<분류>: <변경 내용>` 형식을 사용한다. 미완성 PR은 Draft, 병합은 별도 요청과 저장소 조건을 따른다.
