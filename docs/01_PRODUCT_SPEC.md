# 빌드로그 제품 명세

갱신일: 2026-09-27 · 상태: **문답·레드팀·사용자 결정(2026-09-26) 반영본 / 구현 전** · 표기 기준: [README](README.md)

## 1. 제품 정의

**개발 과정을 공유하는 프로젝트 SNS.** 앱·웹·게임을 만드는 사람이 오늘 만든 화면이나 유튜브 링크에 짧은 설명을 붙여 올리고, 프로젝트의 변화 과정을 공개 페이지에 쌓는다. 새 게시물이 나올 때마다 프로젝트를 다시 발견할 기회를 만든다. [인계 기준]

재노출은 기본 제공 가치(기본 기능)이며 차별점 후보는 **붙여넣기 하나로 게시 / 유튜브·Shorts devlog 링크 게시 / 정직한 공식 콘텐츠**다. 외부 소개는 새 게시·프로젝트 타임라인의 실제 동작 중심으로 설명한다. Q4·BR-004·경쟁 비교 카피 금지는 유지한다. [확정, 사용자 2026-09-26] (D1·Q21)

- 실제 서비스 이름은 **빌드로그(BuildLog)**, 프로젝트 식별 이름은 `buildlog`다. `buildlog-showcase`는 별도 소개 사이트다.
- 한국어 사용자를 우선한다. “국내 유일” 같은 경쟁 우위의 사실 주장은 검증되지 않았으므로 제품 카피에 쓰지 않는다.
- Next.js 기반 웹 서비스로 기획한다. 모바일 브라우저에서 올리고 구경하는 흐름을 우선 설계한다. Next.js는 [현재 요청], 모바일 우선은 [제안]이다.
- 과제 조건인 회원가입·로그인, CRUD, 지도/위치, 결제·취소·내역을 포함한다. [인계 기준] 개발 기간은 최대 40일이며 작업별 일정·진행 순서는 강제하지 않는다. [사용자 정정, 2026-09-17]

## 2. 문제·가치·목표

| 문제 | 제공 가치 | 제품에서 확인할 행동 |
|---|---|---|
| 긴 개발 글을 별도로 쓰기 어렵다 | 이미 만든 화면·영상·링크로 간단하게 게시 | 프로젝트 선택 → 이미지 또는 링크 → 짧은 설명 → 게시 |
| 게시물이 흘러가면 프로젝트의 맥락을 잃는다 | 하나의 프로젝트 페이지에 변화가 누적 | 피드에서 프로젝트로 이동해 이전 게시물·Release 열람 |
| 한 번 출시하고 나면 다시 소개하기 어렵다 | 새 개발 게시물로 재노출 | 새 게시 후 피드·최근 업데이트 목록에 반영 |
| 초기 사용자 수가 적으면 볼거리가 부족하다 | 공식 카드·명시된 데모가 사용 방법과 볼거리 제공 | 실제 사용자 게시물이 없어도 유효한 콘텐츠 열람 |

회원 수·매출·활성 사용자 목표치는 미정이다. 초기 제품 평가는 `프로젝트 생성 → 첫 게시`, `게시 → 프로젝트 페이지 열람`, `프로젝트 팔로우 → 다음 게시물 열람` 같은 실제 행동으로 관찰한다. 데모·운영자 활동은 실제 사용자 행동 지표에서 제외하고 별도 집계한다. [제안]

최소 관찰 단위는 다음 행동 이벤트 5개로 제안한다(K-2). 기록 시점·제외 기준은 [기술 명세 §8](03_TECH_SPEC.md#행동-이벤트)에서 정의한다. 이 5개만으로 다음 게시물 열람이나 가입·체류 등 모든 전략 지표가 측정되는 것은 아니며, 추가 기록 여부는 미정이다. [제안]

| 행동 | 이벤트 | 관찰할 내용 [제안] |
|---|---|---|
| 프로젝트 생성 | `project_created` | 실제 사용자의 프로젝트 생성과 첫 게시의 연결 |
| 게시 | `post_published` | 프로젝트별 첫 게시·후속 게시 발생 |
| 프로젝트 페이지 열람 | `project_viewed` | 게시 후 프로젝트 페이지로 이어지는 열람 |
| 공유 클릭 | `share_clicked` | 공개 URL 복사·공유 기능의 사용. 외부 공유 완료로 해석하지 않음 |
| 프로젝트 팔로우 | `project_followed` | 관심 있는 프로젝트에 관계를 맺는 행동 |

행동 이벤트의 보존 기간은 30일 후 삭제 또는 익명화(Q13 상수 재사용 [확정 원칙 / 기본값은 제안, 구현 시 변경 가능] [기본값 제안])이며 비회원 세션을 가입 계정·다른 기기에 연결하지 않는다. 집계 접근은 운영자 역할만 허용한다. [확정, 사용자 2026-09-26] (D8·Q20). FR-007의 작성자 본인 통계와는 별도이며 구현 계약은 [기술 §8](03_TECH_SPEC.md#행동-이벤트)을 따른다.

## 3. 사용자와 소유 구조

| 사용자 | 목적 | 주요 행동 |
|---|---|---|
| 인디 개발자 | 작업을 가볍게 알리고 포트폴리오 축적 | 프로젝트 생성, 게시, Release, 링크 공유 |
| 소규모 팀·개발사 | 팀 프로젝트 진행 상황 소개 | 팀명·소개·선택적 위치 표시, 프로젝트 운영 |
| 동료 개발자·관심 방문자 | 새로운 앱·웹·게임 발견 | 비회원 열람, 로그인 후 반응·저장·팔로우 |
| 운영자 | 초기 콘텐츠 공급과 서비스 관리 | 공식 카드 검수·예약·게시, 신고 처리, 결제 오류 확인 |

개발자 프로필이 여러 프로젝트를 갖고, **사용자 게시물은 정확히 하나의 프로젝트에 연결**된다. 공식 카드에는 이 제약을 강제하지 않는다. [인계 기준]

팀이 대상이라는 사실과 공동 편집 기능은 별개다. **MVP는 한 계정이 프로젝트를 관리하고 팀명은 소개 정보로 표시**한다. 초대·공동 편집·소유권 이전은 이후 범위다. 계정을 공유하는 방식을 팀 기능으로 안내하지 않는다. [확정, Q2]

## 4. 핵심 흐름

```text
비회원 피드/프로젝트 열람
  → 가입·로그인 → 프로필 작성 → 프로젝트 생성
  → 오늘 만든 것 게시 → 피드 + 프로젝트 타임라인 동시 반영
  → 프로젝트 공개 링크 공유

방문자 → 게시물 발견 → 프로젝트 열람 → 좋아요/저장/팔로우
제작자 → 새 게시물 또는 Release → 프로젝트를 다시 발견할 기회
운영자 → 공식 콘텐츠 초안 → 검수 → 예약/게시 → 피드 공급
제작자 → 홍보 상품 선택 → 결제 → 추가 노출 → 내역/취소
```

화면 목록과 모든 주요 페이지의 ASCII 구조는 [UI/UX 명세](02_UI_UX.md)에 둔다. 계정·프로젝트·게시물·공식 카드·유료 노출의 구분은 [용어집](../CONTEXT.md)에서 관리한다.

## 6. 기능 요구사항

### FR-001 회원·인증·프로필

**목적:** 개발자 단위로 프로젝트와 게시물을 관리한다.

- 공개 콘텐츠는 로그인 없이 열람한다. 작성·반응·저장·팔로우·결제는 로그인 후 가능하다. [제안]
- 최초 인증 후 표시 이름·중복 없는 핸들을 정하고 프로젝트 생성으로 안내한다. 외부 인증 실패 시 작성하던 문맥으로 돌아올 수 있어야 한다.
- Supabase Auth로 GitHub·Google 가입/로그인을 제공한다. 이메일 가입은 MVP에 추가하지 않는다. [확정, Q1] 핸들 정규화·예약어·변경 정책은 구현 설계에서 구체화한다.
- Supabase Auth 제공자의 기본 계정 연결 동작을 따른다. 소유 확인 없는 임의 병합은 금지하며 수동 연결 UI는 MVP에서 제외한다. [확정, 사용자 2026-09-26] (D9·Q22)
- 프로필에는 소개·아바타·외부 링크·프로젝트 목록·선택적 위치를 표시한다. 공개 이메일·실명·정확한 주소를 기본 요구하지 않는다.
- **완료 조건:** 가입·재로그인·로그아웃, 중복 핸들, 만료 세션, 다른 사람의 프로필 변경 차단을 확인한다.

### FR-002 프로젝트 CRUD

- 이름·한 줄 소개·사용 기술을 온보딩 입력으로 받는다. 분류(앱/웹/게임), 대표 이미지·스크린샷·GitHub/웹사이트 링크·현재 단계는 추가 편집한다. 분류는 생성 시 선택이며 미분류 상태를 허용하는 안을 제안한다.
- 단계는 `개발 중 / 베타 / 출시`를 권장한다. 버전 문자열과 제품 단계는 서로 다른 정보다. [제안]
- 프로젝트 페이지에는 제작자, 기술 칩, 링크, 스크린샷, 개발 타임라인, Release가 보인다. 공개 URL을 복사할 수 있다.
- 게시물이 있는 프로젝트 삭제는 영향 범위를 먼저 보여준다. 진행 중인 유료 노출·취소 미확정 결제가 있으면 바로 삭제하지 않고 정리 경로로 안내한다. [제안]
- **완료 조건:** 생성·목록·상세·수정·삭제, 소유권 검증, 삭제 후 검색·피드·직접 링크 반영을 확인한다.

### FR-003 게시물 작성·편집·삭제

- 입력창 하나, 프로젝트 선택 칩, 첨부 영역, 게시 버튼을 제공한다. 프로젝트 선택은 필수다. [인계 기준]
- 유형을 먼저 고르지 않고 내용과 첨부를 자동 판별한다. **내용은 글·미디어·지원 링크 중 하나 이상**이면 게시할 수 있다. 짧은 설명은 권장하지만 필수는 아니다. [확정, Q9]
- 텍스트만 있는 개발 게시물도 허용한다. 글·여러 이미지/GIF·대표 링크 하나를 함께 첨부할 수 있다. [확정, Q9]
- 본문은 2,000자, 이미지/GIF는 합계 4개, 정적 이미지 1개당 10MB·GIF 1개당 20MB·첨부 전체 40MB까지 허용한다. 대표 링크는 1개이며 복수 URL 중 사용자가 선택을 바꿀 수 있다. 다른 URL은 일반 링크로 둔다. [확정, Q9 후속]
- 최근 사용 프로젝트를 제안하되 게시 전에 이름을 분명히 보여준다. 다른 프로젝트로 자동 변경하지 않는다.
- 편집·삭제는 프로젝트를 관리하는 계정에만 허용한다(Q2). 편집으로 최초 게시 시각을 바꾸거나 새 글처럼 다시 올리지 않는다(Q4). 삭제 즉시 공개를 종료하고 30일 유예 후 원문·파일을 정리한다(Q13).
- **완료 조건:** 한 번의 게시가 피드와 프로젝트 타임라인에 같은 게시물로 나타나고, 재시도·더블 클릭으로 중복 생성되지 않는다. 실패 시 입력과 첨부 선택을 유지한다.

### FR-004 미디어·외부 링크

- 스크린샷·GIF, YouTube/Shorts 영상 카드, GitHub 저장소 카드, 일반 웹사이트 미리보기를 지원한다. 직접 영상 업로드는 제외한다. [인계 기준/제안 범위 구분은 5절]
- 영상은 썸네일·재생 동작·알 수 있을 때의 길이를 표시한다. 길이를 얻지 못하면 숫자를 만들지 않는다. 카드에서 재생하거나 원본으로 이동할 수 있다.
- 삭제·비공개·임베드 불가 영상과 미리보기 실패 URL은 원문 링크로 남긴다. 외부 서비스 응답 실패가 전체 게시를 막지 않는 안을 권장한다.
- 이미지의 원본 비율은 보존하고 피드의 정사각 프레임과 원본 열람을 구분한다.
- **완료 조건:** 각 입력의 정상·실패·삭제된 외부 콘텐츠, GIF 동작, 위험 URL·잘못된 파일 거부를 확인한다.

### FR-005 피드·재노출

- 사용자 게시물과 공식 카드를 구분해 함께 보여준다. 일상 게시물은 제품 범위에 포함하지 않는다.
- 기본 정렬은 최신 게시순이다. 새 게시물 한 건이 프로젝트로 진입하는 경로이며, 같은 글을 복제해 상단으로 올리지 않는다. [확정, Q4]
- 프로젝트의 최근 활동 시각은 가장 최근의 공개 게시물 또는 Release를 기준으로 한다. 편집·좋아요로 자연 노출 시각을 갱신하지 않는다. [확정, Q4] 유료 구매에 따른 추가 노출은 FR-011의 Q6/Q12 정책을 따른다.
- 메인은 사용자 글이 충분할 때 사용자 게시물 5개당 공식 카드 1개를 넣고, 부족할 때 공식·데모로 보충한다. 팔로잉에는 팔로우한 프로젝트의 게시물만 표시한다. [확정, Q14] 사용자 글의 최신순은 유지하고 같은 카드를 복제해 빈자리를 채우지 않는다.
- 초기 개인화 비율 70/30, 활동 점수, 주 2회 Boost는 채택하지 않았다. 유료 노출은 광고 영역의 순환 방식(Q12)이며 슬롯·순환 기본값은 FR-011의 Q16 정책을 따른다.
- **연속 카드 접기:** 전체·팔로잉 자연 피드에서 같은 프로젝트의 게시물이 연속 2건 이상이면 최신 1장만 보이고 “이 프로젝트의 이전 게시물 N개 펼치기”를 붙인다. 펼치면 원래 위치·최신순 그대로 보이며, 접힌 게시물에 Release가 있으면 “Release 포함”을 표시한다. [확정, 사용자 2026-09-26] (D2·K-12, BR-017)
- 접기는 한 페이지 응답 안에서만 적용한다 [확정 원칙 / 기본값은 제안, 구현 시 변경 가능] [기본값 제안]. Q4 정렬·`published_at`은 바꾸지 않고 프로젝트 타임라인은 전체 기록을 유지한다. 공식 카드·광고는 접기 대상이 아니다. [확정, 사용자 2026-09-26]
- **완료 조건:** 새 게시·삭제·숨김·페이지 추가 로딩에도 중복 카드나 숨긴 콘텐츠의 재등장이 없다. 메인의 5:1 혼합·콘텐츠 부족 시 대체를 확인하고, 팔로잉에는 팔로우한 프로젝트의 게시물만 보인다. 연속 카드 접기·펼치기의 원래 위치·Release 포함 표시와 페이지 경계·전체 타임라인 보존을 확인한다.

### FR-006 프로젝트 타임라인·Release

- 이미지·영상·링크 게시물과 Release가 같은 타임라인에 시간순으로 쌓인다. 최신 항목부터 보여주는 안을 권장한다.
- Release는 별도 작성 버튼이 있는 특별한 게시물 유형이다. 프로젝트에 연결된 한 게시물로 피드·타임라인에 한 번씩 표시한다. [확정, Q10]
- Release는 버전·제목·변경 내용을 담고 관련 링크·첨부를 선택적으로 받는다. **버전명은 개발자의 자유 원칙**을 따른다. SemVer 등 형식·숫자 순서·중복 금지·게시 후 버전명 고정 규칙을 강제하지 않는다. 버전명도 편집할 수 있다. [확정, Q10 후속의 자유 원칙 반영]
- 버전 문자열을 대소 비교해 최신 버전을 정하지 않는다. 프로젝트의 현재 버전은 최신 공개 Release의 표시값을 사용하고, 해당 Release를 삭제하면 다음으로 최근인 공개 Release에서 가져오는 설계안을 둔다. 버전명 수정으로 최초 공개 순서를 바꾸지 않는다.
- **완료 조건:** Release가 피드/타임라인에서 한 번만 보이고 일반 게시물과 구별된다. 자유 버전명·같은 버전명·수정이 허용되며, 삭제 후 공개 버전 표시와 최근 활동이 일치한다.

### FR-007 좋아요·저장·팔로우·공유

- 좋아요·저장·프로젝트 팔로우를 제공한다. 팔로잉 탭에서 팔로우한 프로젝트의 다음 게시물을 본다. 개발자 팔로우는 MVP에 포함하지 않는다. [확정, Q3]
- 저장 목록은 본인만 본다. 좋아요·팔로우는 취소할 수 있고 중복 요청을 해도 한 관계만 존재한다.
- 공유는 공개 URL 복사와 가능한 환경의 공유 기능을 제공한다. SNS용 이미지 자동 생성은 이후 제안이다.
- 좋아요·팔로워·조회 수는 기본 카드에서 숨기고 실제 행동 상태를 보여준다. 가짜 수치는 금지한다. [확정, Q3]
- 댓글과 별도 알림함은 이후 범위다. MVP에 말풍선·알림함 버튼을 노출하지 않는다. 제출 결과·오류·결제 상태 같은 화면 내 안내는 유지한다. [확정, Q3]
- 작성자 본인에게 **본인 게시물·본인 프로젝트의 좋아요 수·저장 수·프로젝트 팔로우 수**를 제공한다. 프로젝트 관리는 프로젝트별 집계, 게시물 상세 본인 보기는 해당 글의 집계, 프로필 본인 보기는 본인 프로젝트별 집계를 보여준다. 본인만 보는 화면에 표시하고 기본 카드 숫자 숨김(Q3)·가짜 반응 금지를 유지한다. [확정, Q19] [확정, 사용자 2026-09-26] (D7). K-1의 결정 의존성은 해소됐으며 댓글·알림함은 이후 범위다.
- 출시 전 인터뷰는 불가하다(사용자 결정 2026-09-26). 본인 통계 제공 결정은 제작자 보상 효과의 검증 완료를 뜻하지 않으며 출시 후 실제 게시·열람 행동으로 검증한다. 댓글·알림 요구가 생기면 Q3·ADR-0003 재검토 사유로만 다룬다.
- **완료 조건:** 로그인 복귀, 반응 취소, 비공개 저장, 삭제 콘텐츠 처리, 팔로우 해제 반영을 확인한다. 본인 통계의 실제 집계·본인 화면 표시·타인 접근 차단·기본 카드 숫자 숨김을 확인한다.

### FR-008 탐색·검색

- 프로젝트명·소개·기술 태그·분류로 프로젝트를 찾는다. 최신 업데이트순을 먼저 제공한다. 미분류 프로젝트도 전체 목록과 텍스트·기술 검색에 포함하며 특정 분류 필터에서만 제외한다. [제안]
- 인기순·지금 뜨는 프로젝트·오늘 출시 섹션은 유효한 기준과 데이터가 준비된 후 추가한다. 빈 목록에 임의 순위나 활동 수치를 넣지 않는다.
- **완료 조건:** 조합 필터·결과 없음·검색 초기화·삭제/숨김 프로젝트 제외가 동작한다.

### FR-009 공식 카드·데모

- 공식 카드·데모 프로젝트의 역할은 비회원 이탈 방지·사용 방법 안내로 둔다. 가입 유도 효과를 전제하지 않으며, 가입 관련 검증은 S-1·S-5에서 다룬다(K-7). [제안]
- 공식 카드 3종: **오늘의 만들기 주제 / 개발 팁과 소식 / 이번 주 프로젝트**. 소식은 인디 개발·메이커 관련 뉴스와 포럼의 프로젝트 소개를 중심으로, 때로는 주요 업계 최신 뉴스도 다룬다. [인계 기준 + Q5 추가 요청]
- “공식”은 빌드로그가 편집한 카드라는 뜻이며 원문 작성자의 공식 참여·추천을 뜻하지 않는다. 외부 뉴스·포럼 글에는 원문 출처·게시일·링크를 표시하고 한국어 요약·소개로 연결하는 방식을 제안한다. 원문 전체·댓글 모음의 자동 재게시는 범위에 두지 않는다.
- 외부에서 소개한 제작자·프로젝트를 빌드로그 가입자나 등록 프로젝트로 자동 생성하지 않는다. “이번 주 프로젝트”는 실제 등록된 공개 프로젝트를 대상으로 하며, 외부 프로젝트 소개는 출처가 있는 소식 카드로 구분한다. [제안]
- 운영자가 관리하는 BuildLog 자체 프로젝트에는 실제 개발 내용을 게시할 수 있다. 그 글도 일반 프로젝트 연결 규칙을 따른다.
- 데모 프로젝트·인물·게시물은 목록과 상세에서 “데모”로 구별한다. 작은 타이머·달빛 정원사·레시피 메모는 재사용 가능한 허구 예시이며 실제 유저가 아니다.
- 데모 프로젝트는 **작은 타이머·달빛 정원사·레시피 메모 3개**로 시작한다. 기능이 바뀌거나 예시가 낡으면 교체한다. 좋아요·저장을 허용하되 실제 사용자 집계에서 제외하고 “데모” 표시를 유지한다. [확정, 사용자 2026-09-26] (D5·Q17). 데모를 결제·인기 집계 대상에서 제외하는 기존 제안은 유지한다.
- **완료 조건:** 실제 사용자가 0명이어도 공식/데모가 구분된 볼거리를 제공하고, 실사용자 수·후기·활동을 가장하지 않는다.

### FR-010 콘텐츠 자동화·관리자

- MVP에 **외부 RSS 수집과 AI 원고 생성**을 포함한다. 인디 관련 뉴스·포럼을 주기적으로 가져오고 주요 업계 소식도 다룬다. 내부 프로젝트·운영자 소재도 함께 사용한다. [확정, Q5 및 추가 요청]
- 흐름: 허용 RSS/공식 API·내부 소재 → 수집·정규화 → 중복·품질 필터 → AI 원고/템플릿 초안 → 카드 미리보기 → 관리자 수정·승인 → 예약/게시 → 게시 중단. 수집과 공개의 주기는 별개로 둔다. 외부 수집 실패와 AI 생성 실패는 각각 확인·재시도할 수 있게 한다.
- 인디/업계 소식은 수집한 출처를 근거로 AI 한국어 초안을 만들고, 만들기 주제·등록 프로젝트 소개는 내부 소재로 작성할 수 있다. 단순 라이브러리 릴리스 공지에만 소스를 한정하지 않는다.
- **하루 1회 수집·AI 초안 하루 최대 5개·관리자 승인 후 하루 최대 2개 게시**로 운영한다. 승인되지 않은 원고는 공개하지 않으며, 예약/수동 실행으로도 일일 게시 한도를 우회하지 않는다. [확정, Q8] 일일 상한 집계는 KST 00:00 기준이며 예약·게시 시각은 KST로 표시한다. 지연·재시도는 원래 날짜 집계를 유지하고 중복 발행하지 않는다. [확정, 사용자 2026-09-26] (D10·Q23). 수집 작업의 실행 시각은 구현 설정으로 둔다.
- 뉴스·포럼 글의 게시 시각과 다루는 사건 날짜를 구분하고, 오래된 글의 재수집을 최신 소식으로 포장하지 않는다. 포럼의 개인 경험·의견·주장은 보도된 사실처럼 단정하지 않고 원문 작성자에게 귀속한다. 동일 사건의 여러 링크를 여러 카드로 중복 발행하지 않도록 검수한다. [제안]
- AI는 GPT 계열을 우선 사용할 예정이다(Q7). 모델은 GPT 5.6 Luna, AI 비용은 GPT Pro 5X 구독 바탕이며 API 월 상한 기본값은 $5 [기본값 제안]이다(사용자 2026-09-27). 원문 이용·보존 범위는 실제 연동 전에 정한다. 허용 소스는 Q15, 집계 시간대는 Q23 확정 정책을 따른다. 모델·비용 상한이 설정되지 않으면 유료 생성을 실행하지 않는다. 소스 미허용, 내용 부족, 중복, 비용 상한 초과는 게시가 아니라 보류 사유다. 내부 템플릿 성공만으로 외부 RSS·AI 범위까지 완료 처리하지 않는다.
- 초기 허용 소스는 [기술 명세 §7](03_TECH_SPEC.md#실제-수집-경로를-확인한-소스-후보)의 **GeekNews·Show HN·itch.io devlogs·Ars Technica** 4개다. Ars Technica는 업계 뉴스 용도로만 사용한다. 적합 소재가 부족한 날은 발행하지 않아도 되며 Q8 상한은 의무가 아니다. [확정, 사용자 2026-09-26] (D3·Q15). 주간 다이제스트 형식 채택은 7일 관찰 후 결정한다. [미정 유지]
- 외부 팁·소식에는 출처와 기준 날짜를 표시한다. 출처가 없거나 이용 조건을 확인하지 못한 초안은 게시하지 않는다. AI 생성은 검수 생략의 근거가 아니다.
- 추천 대상 삭제, 중복 실행, 예약 작업 실패 때 자동으로 가짜 대체 카드를 생성하지 않고 운영자 확인 대상으로 돌린다.
- **완료 조건:** 실제 허용 RSS/API에서 수집 → AI 원고 → 검수 → 게시를 확인한다. 승인 전 비노출, 하루 초안 5개/게시 2개 상한, 중복 소재·수집 장애·AI 실패·비용 제한·잘못된 출처·예약 재시도를 검증한다.

### FR-011 유료 노출·결제·취소·내역

- Featured 테스트 결제의 MVP 역할은 **과제 조건 충족과 결제·취소·대사 파이프라인 기술 검증**이다. 테스트 결제 데이터를 지불 의사나 수요 신호로 해석하지 않는다(K-8). [제안]
- 유료 노출은 보조 기능이다. 자연 재노출과 별도 공간에 **광고**를 표시하고 구매로 자연 피드의 게시 시각을 조작하지 않는 안을 권장한다.
- MVP 상품은 프로젝트 Featured 한 종류다. Toss 테스트 결제 금액 1,000원·7일로 제공한다. 금액은 테스트용이며 실판매가가 아니다. [확정, Q6/Q12]
- 흐름: 내 프로젝트 → 상품·기간·취소 조건 확인 → 주문 → 테스트 결제 → 서버 확인 → 시작 대기 → 사용자가 **노출 시작** → 7일간 진행 → 종료. 광고 영역에서 진행 중인 프로젝트들과 순환 노출하며 조회·클릭 수를 보장하지 않는다. [확정, Q12]
- **테스트 결제·전액 취소·내역**을 구현한다. 실제 금액 차감이 없음을 표시하며 실결제 전환은 이후 범위다. [확정, Q6] 테스트 금액은 실판매 가격이나 매출로 표시하지 않는다.
- 노출 시작 전에는 사용자가 전액 취소할 수 있다. 시작 후 사용자 임의 취소는 제공하지 않으며, 미제공·서비스 오류는 운영자가 전액 취소한다. [확정, Q12] 시작과 취소가 동시에 요청되면 하나만 적용한다. 실결제 약관 검증이 끝난 것으로 취급하지 않는다.
- 광고 영역은 슬롯 1개에서 활성 노출끼리 균등 순환한다 [확정 원칙 / 기본값은 제안, 구현 시 변경 가능] [기본값 제안]. 같은 프로젝트에 활성 또는 시작 대기 주문이 있으면 추가 구매할 수 없다. 결제 후 30일 안에 시작하지 않은 주문은 운영자 전액 취소 대상이며, 30일은 Q13 유예와 같은 상수를 재사용한다 [확정 원칙 / 기본값은 제안, 구현 시 변경 가능] [기본값 제안]. [확정, 사용자 2026-09-26] (D4·Q16). Q12 금액·기간·수동 시작·취소 경계는 유지하며 시작하지 않은 결제가 자동 노출·매출로 전환되지는 않는다.
- 결제창 닫기는 결제 완료 후 취소와 구분한다. 결제·취소 결과가 불명확하면 확인 중으로 남기고 재결제를 유도하지 않는다.
- **완료 조건:** 결제·전액 취소·내역, 중복 요청, 서버 응답 지연, 취소와 노출 시작 동시 요청, 타인 내역 접근 차단을 검증한다. 동일 프로젝트 활성/시작 대기 주문의 추가 구매 차단과 30일 미시작 주문의 운영자 전액 취소·기록을 확인한다.

### FR-012 프로필 위치·지도

- 지도는 개발자·팀 소개의 보조 정보다. 위치 없이 가입·프로젝트 생성·게시가 가능하다. [인계 기준, 선택 입력은 확정 Q1]
- 위치는 기본 비공개다. 원할 때 시·군·구와 해당 지역 중심 지도만 공개한다. 정확한 개인 주소·업무 주소·현재 위치는 수집하지 않는다. [확정, Q11]
- 지역 코드·지역명·대표 좌표로 표시하며 개인의 정확한 좌표를 저장한 뒤 화면에서만 숨기는 방식으로 구현하지 않는다.
- 지도 제공자는 Kakao Maps로 확정했다. [확정, Q1]
- **완료 조건:** 지역 등록·변경·비공개 전환, 지역 검색 실패, 지도 로딩 실패의 텍스트 대체, 공개 수준을 넘는 정보 유출 방지를 확인한다.

### FR-013 신고·숨김·운영 권한

- 프로젝트/게시물의 스팸·권리 침해·개발과 무관한 콘텐츠를 신고하고 운영자가 사유와 함께 숨김/복원한다. [확정, Q13]
- 신고 자체가 자동 삭제·자동 환불·자동 계정 정지를 발생시키지는 않는다. 유료 노출이 걸린 대상의 제재는 지급·보상 확인 대상으로 묶는다.
- 운영자는 **사용자 본인 계정에 명시적 운영자 역할**을 부여한다. 개발자라는 이유로 자동 권한을 주지 않는다. 승인·게시·숨김·복원·취소 행위는 `moderation_actions` 등에 기록한다. [확정, 사용자 2026-09-26] (D6·Q18)
- 최소 감사 항목은 **조치 종류·사유·시각·조치자·대상 ID**다. 이의 제기는 설정 화면의 문의 링크(이메일, 주소는 더미 `contact@buildlog.example`로 진행하고 출시 전 교체 [확정, 사용자 2026-09-27])로 받는다. [확정, 사용자 2026-09-26] (D11·Q24). Q13 즉시 공개 종료·30일 정리는 유지하고, 사용자 삭제·탈퇴에 적용한 30일 유예를 운영자 숨김의 자동 삭제 기한으로 혼동하지 않는다.
- **완료 조건:** 일반 회원의 관리자 접근 차단, 숨김의 모든 공개 화면 반영, 조치 이력을 확인한다.

### FR-014 설정·계정 종료

- 프로필·연결된 로그인 정보·위치 공개·결제내역·로그아웃으로 연결한다. 실제 지원하는 항목만 표시한다.
- 설정 화면에 신고·운영 조치에 이의를 제기할 **문의 링크(이메일)**를 제공한다. 주소는 더미 `contact@buildlog.example`(예약 예시 도메인)로 진행하고 출시 전 실주소로 교체한다. 실제 수신되는 임의 이메일을 기입하지 않는다. [확정, 사용자 2026-09-27] [확정, 사용자 2026-09-26] (D11·Q24)
- 사용자 삭제·탈퇴는 즉시 공개를 종료하고 30일 유예 후 원문·파일을 정리한다. 진행 중 결제·노출은 먼저 취소 또는 종료해야 탈퇴할 수 있다. 운영 확인용 기록은 콘텐츠와 분리하고 최소화한다. [확정, Q13]
- 실결제 거래의 법적 보존 정책은 실결제 전환 전에 별도로 정한다. 30일 유예가 사용자용 복구 화면·무제한 기록 보존까지 포함하는 것은 아니다.
- **완료 조건:** 삭제 전 영향 안내, 재인증, 즉시 공개 종료, 30일 경과 정리, 진행 중 거래 보호를 검증한다.
