## 1. 목표와 현재 전제

작성된 제품·화면·기술·작업 로드맵을 구체적인 사례로 검토하고, 사용자가 고른 정책으로 갱신한다. 이번 계획은 앱 구현 계획이 아니다.

이미 제공된 기준: Next.js, 프로젝트 필수 연결, 같은 게시물의 피드/타임라인 노출, 쉬운 미디어/링크 게시, 공식 콘텐츠 자동화, 지도와 결제·취소·내역을 포함한 과제 조건. 이 항목의 승인 여부를 반복 질문하지 않는다.

확정되지 않은 원래 제안은 침묵을 승인으로 해석하지 않는다. 기술 사실은 환경·공식 자료로 조사하고, 제품의 선택은 사용자 답변으로 확정한다. 이번에는 별도 Skill 호출 도구가 없어 해당 `SKILL.md`와 형식 문서를 직접 읽어 적용했다.

**일정 정정(2026-09-17):** 사용자는 “40일은 최대 일정이고 작업이 일정을 따라 가진 않는다. 따라서 작업 일정과 순서를 강제 하진 않을 것이다.”라고 명시했다. 이전의 일차별 배정과 “40일 개발 순서표” 해석은 폐기한다. 최대 기간은 유지하되 작업 선택·병렬 진행·통합은 우선순위와 실제 의존성에 따라 결정한다.

## 4. 첫 라운드 — 답변 기록

2026-09-17에 8개 질문 모두 답변을 받았다. 각 항목 첫머리의 **확정 답변**이 현재 결정이며, 그 아래 질문·권장안은 당시 검토 근거다. 특히 Q5는 최초 권장안보다 범위를 확장했다.

### Q1 기반 스택·가입 방식

**확정 답변:** “제안 조합 채택 (권장)”. Supabase(Auth/DB/Storage)·Vercel·GitHub/Google 로그인·Kakao 지도를 사용하고 위치 입력은 선택이다. 이메일 가입 추가는 선택하지 않았다.

❓ **Next.js 외의 기반은 어떤 조합으로 시작할까요?**

➡️ **Supabase(Auth/DB/Storage) + Vercel, GitHub·Google 로그인, Kakao 지도**를 권장한다. 위치는 선택 입력으로 두고 결제는 Q6에서 정한다. 이메일/비밀번호 가입이 과제에 명시돼 있다면 그 조건에 맞춰 바꾼다. 현재 인계된 과제 조건에는 로그인 방식까지 정해져 있지 않다.

영향: FR-001/FR-012, TECH §1/3, ROADMAP 앱·회원/위치 작업.

### Q2 프로젝트 관리 주체

**확정 답변:** “한 계정이 관리 (권장)”. 팀명은 소개 정보이며 초대·공동 편집·소유권 이전은 MVP 이후다.

❓ **팀 프로젝트도 처음에는 계정 한 명이 관리할까요, 팀원 공동 편집까지 넣을까요?**

➡️ **한 명이 관리하고 팀명은 소개 정보로 표시**하는 안을 권장한다. “팀원이 퇴사했을 때 누가 수정하는가”까지 해결하려면 초대·역할·소유권 이전이 함께 필요하다. 공동 관리가 핵심이면 지금 포함시키고 일정을 재산정한다.

영향: FR-002, 프로젝트 소유·게시 권한·삭제·결제 구매자 관계.

### Q3 소셜 경험

**확정 답변:** “권장 구성 채택”. 프로젝트 팔로우·좋아요·저장을 제공한다. 댓글·별도 알림함·개발자 팔로우는 이후로 두고 카드 반응 숫자는 숨긴다.

❓ **첫 버전에서 팔로우·댓글·알림·반응 숫자를 어디까지 제공할까요?**

➡️ **프로젝트 팔로우 + 좋아요·저장, 댓글·별도 알림함은 이후, 카드의 반응 숫자는 숨김**을 권장한다. 팔로잉 탭에서 다음 게시물을 본다. 개발자 팔로우, 댓글, 실제 숫자 공개가 중요하면 필요한 항목을 지정한다. 실제 수치 표시 여부와 가짜 수치 금지는 별개다.

영향: FR-007, SCREEN-001/005/006/015, social 모델, ROADMAP 발견·소셜 작업.

### Q4 기본 피드

**확정 답변:** “최신순과 새 게시 재노출 (권장)”. 편집·좋아요로 게시 시각을 올리지 않는다. 구체적인 혼합 간격은 Q14에서 정한다.

❓ **새 기록 순서로 발견하게 할까요, 활동 점수로 순위를 매길까요?**

➡️ **최신순 + 새 게시물에 따른 프로젝트 재노출**을 권장한다. 편집·좋아요로 게시 시각을 갱신하지 않는다. 공식 카드와 유료 노출의 혼합 방식은 이 답을 바탕으로 정한다.

영향: FR-005/FR-008, BR-004, 피드 커서·활동 값·데이터 집계.

### Q5 공식 콘텐츠 자동화

**확정 답변:** “외부 RSS·AI 원고까지 포함”. 초기의 내부 소재만으로 시작하는 권장안은 채택하지 않았다.

**추가 요청:** “인디 관련 뉴스 포럼 같은 걸 주기적으로 가져오고 싶고, 때론 업계 최신 뉴스도 다룬다.” 앱·웹·게임의 인디 개발·메이커를 중심으로 주요 업계 소식을 함께 다루며 라이브러리 릴리스 소식에만 한정하지 않는다. 구체적인 출처·발행 주기·검수·예산은 Q8/Q7에서 정한다.

❓ **40일 안에서 자동화의 범위를 어디까지 가져갈까요?**

➡️ **내부 프로젝트·운영자 소재 → 템플릿 초안 자동 생성 → 관리자 승인 → 예약 게시**를 먼저 권장한다. 개발 팁·소식은 운영자가 출처와 내용을 입력할 수 있다. 외부 RSS 수집·AI 원고까지 첫 버전에 포함할 수도 있지만 소스·모델·비용·품질 검증이 추가된다. 어떤 선택이든 공식 3종 카드와 자동화 자체는 유지한다.

영향: FR-009/FR-010, 수집 소재·AI 작업 모델, 운영 화면, ROADMAP 콘텐츠·운영 작업. 결제 작업과의 선후 순서를 강제하지 않는다.

### Q6 유료 상품과 결제 범위

**확정 답변:** “Featured 한 상품·테스트 결제 (권장)”. 전액 취소·내역까지 포함하며 실결제·다른 상품은 이후다. 기간·금액·취소 시점은 아래 Q12에서 확정했다.

❓ **첫 상품을 프로젝트 Featured 하나로 두고 테스트 결제부터 완성할까요?**

➡️ **Featured 한 상품 + 테스트 결제·전액 취소·내역**을 권장한다. 과제 기능을 검증한 뒤 실결제를 별도 전환한다. 가격·기간·노출 시작·취소 가능 경계는 상품 선택 후 정한다. 실제 결제가 과제 조건인지도 이 선택에 함께 명시한다.

영향: FR-011, 상품/주문/노출 모델, ROADMAP 결제·노출 작업, 출시 기준.

### Q9 게시물 구성

**확정 답변:** “혼합 첨부·내용 하나 이상 (권장)”. 글·여러 이미지/GIF·대표 링크 하나를 함께 올릴 수 있고 텍스트만도 허용한다. 개수·용량·글자 수는 후속 질문이다.

❓ **한 게시물에 여러 이미지와 대표 링크 하나를 함께 올릴 수 있게 할까요?**

➡️ **짧은 글 + 여러 이미지/GIF + 대표 링크 하나**, 그리고 **글·첨부·링크 중 하나 이상이면 게시 가능**을 권장한다. 한 장만 올려도 되고 텍스트만 있는 개발 게시물도 허용한다. 유형 선택은 요구하지 않는다. 최대 개수·용량은 이 구성이 정해진 다음 정한다.

영향: FR-003/FR-004, SCREEN-004, post_media/link_previews, 업로드·미리보기 검증.

### Q10 Release의 의미

## 6. 공유된 범위와 답변 반영 절차

두 라운드의 답변을 종합하면, 단일 소유자의 프로젝트 기록과 발견이 중심이며 외부 뉴스 수집·GPT 초안·관리자 검수, 지역 지도, Featured 테스트 결제를 MVP 작업 범위에 포함한다. 최대 기간은 40일이며 작업 일정·순서는 강제하지 않는다. 댓글·공동 편집·실결제는 이후다. 사용자가 명시적으로 미정으로 둔 시간·예산·모델·도메인은 이 범위의 승인과 분리해 관리한다. 이후 답변으로 바뀌면 아래 절차로 갱신한다.

1. 답변의 선택·이유·날짜를 이 계획에 기록한다. 답하지 않은 항목은 대기로 둔다.
2. 용어가 확정되면 즉시 `CONTEXT.md`에 짧은 정의를 반영한다. 구현 세부는 넣지 않는다.
3. 제품/화면/기술/로드맵의 해당 계약을 함께 고친다. 중복되는 정책은 제품 정본을 참조한다.
4. 되돌리는 비용이 크고 대안·선택 이유가 필요한 결정에만 ADR을 쓴다.
5. 다음 질문은 새 답으로 선행 조건이 풀린 항목만 제시한다.
6. 남은 결정과 조정된 범위를 요약해 공유된 이해를 확인한다. 문답 완료와 실제 앱 구현 완료를 구분한다.

### 2026-09-27 PRD 권고안 채택

사용자 “PRD의 권고안으로 기존 문서를 갱신” 결정에 따라 아래 A1~A5를 채택했다 [확정, 사용자 2026-09-27]. 기존 Q1~Q24 답변·D1~D11·ADR 원문은 유지하며 [PRD §7.4](../PRD-buildlog.md#74-가정-아직-확인-못-한-것)의 가정과 실제 검증 결과는 확정 대상이 아니다.

- **A1 성과 기준:** [PRD §4](../PRD-buildlog.md#4-목표와-성과-기준)의 KR1~KR5와 표의 기존 숫자·근거를 그대로 채택하며, 사용자 수·매출 목표는 추가하지 않는다.
- **A2 출시 단계:** [PRD §8](../PRD-buildlog.md#8-출시-계획)의 1차 프로토타입(KR1~KR5·과제 6조건), 2차 발견과 반응(팔로우 → 다음 글 열람 계측), 3차 자동화 운영(실제 소스 카드 1장 발행·결제 불일치 대사 통과)과 완료 기준을 채택하며 2·3차도 첫 버전(MVP) 범위 안이다.
- **A3 시간·재협상:** 핵심 흐름 1 실제 투입 27시간 초과 시 재협상하고 소스 4개 → 1개, 카드 템플릿 3종 → 1종, 관리자 편의 기능 순으로 축소 후보를 검토하되 지도·결제·RSS/AI 자체는 후보가 아니며 자동 축소하지 않는다.
- **A4 행동 기록 구성:** Supabase 자체 `events`·Supabase Cron(`pg_cron`) 30일 정리·서버 발급 HttpOnly 쿠키 30분 절대 만료·SQL 뷰 1개와 관리자 페이지 1개를 [조사 §4](../research/event-tool-check.md#4-제안-채택할-기록-계약과-구체화)와 [기술 §8](../03_TECH_SPEC.md#행동-이벤트)에 따라 채택하며 Q20 완전 준수는 구현 검증 뒤 판정한다.
- **A5 정직성 검사:** KR3의 공식/데모/광고 배지·기본 카드 반응 숫자 없음·광고의 자연 피드 제외 자동 검사 3개를 1차 프로토타입 완료 조건으로 재확인한다.
