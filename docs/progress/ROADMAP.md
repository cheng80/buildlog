# 빌드로그 작업 로드맵

갱신일: 2026-09-27 · 상태: **PRD 권고안 확정 / 1차 프로토타입 착수 준비 / 구현 미착수**

**40일은 최대 기간이다. 작업별 날짜·소요 일수·진행 순서를 강제하지 않는다.** 작업은 현재 우선순위·준비 상태·기술적 의존성에 따라 선택하고, 가능한 항목은 병렬로 진행하거나 합쳐서 완료한다. 40일을 채우기 위해 작업을 나누거나 완료를 미루지 않는다. 시작일·달력 마감일은 미정이며 하루 작업 시간은 2시간으로 확정했다(2026-09-27). 작업별 날짜·순서를 강제하지 않는 원칙은 유지하되 아래 출시 단계는 위험이 큰 것부터 확인하는 기준으로 채택했다 [확정, 사용자 2026-09-27].

Q5와 추가 요청에 따라 **인디 뉴스·포럼 및 주요 업계 소식의 RSS/공식 API 수집·AI 원고 생성**을 MVP 범위에 포함한다. 아래 목록은 작업 범위와 완료 기준을 확인하는 용도이며 위에서 아래로 진행해야 하는 순서표가 아니다. 필요한 검증은 각 기능 작업에 포함하고, 서로 연결된 기능이 준비되면 통합 검증한다. GPT 모델·월 예산·도메인은 실제 연동에 필요한 시점에 정한다.

## 출시 단계 (2026-09-27 확정)

[PRD §8](../PRD-buildlog.md#8-출시-계획)의 출시 단계와 끝났다고 보는 기준을 채택했다 [확정, 사용자 2026-09-27]. KR1~KR5의 숫자·근거는 [PRD §4](../PRD-buildlog.md#4-목표와-성과-기준)를 따른다.

| 단계 | 들어가는 것 | 끝났다고 보는 기준 |
|---|---|---|
| **1차: 프로토타입** | 핵심 흐름 1 + 행동 이벤트 5개 + 정직성 자동 검사 3개 + 공식 카드 내부 3종·데모 3개·5:1 혼합 + 과제 조건 최소(지역 지도, Featured 테스트 결제·취소·내역·수동 시작) | KR1~KR5 전부. 과제 6조건 시연 가능 |
| **2차: 발견과 반응** | 프로젝트 팔로우·팔로잉 탭, 좋아요·저장, Release, 본인 통계, 연속 카드 접기, 검색·태그, 신고·숨김 | 팔로우 → 다음 글 열람 계측 가능 |
| **3차: 자동화 운영** | RSS 수집 → GPT 초안 → 승인 → 게시 상한, 관리자 화면, 소스 관리, 광고 순환·운영자 취소·대사 | 실제 소스에서 카드 1장 발행, 결제 불일치 대사 통과 |
| 이후 | 댓글·알림, 팀 공동 편집, 사람 팔로우, 인기순, 실결제, 공유 이미지, 네이티브 앱 | 필요성 확인 후 |

2차·3차도 첫 버전(MVP) 범위 안이다. 순서는 위험이 큰 것부터이며 독립 준비·검증은 병렬로 진행할 수 있다. 1차 KR5의 이벤트 5개를 확인할 최소 프로젝트 팔로우 동작은 1차에 포함하고 팔로잉 화면은 2차에서 확장한다. KR1의 배포 후 14일 실제 사용자 게시 관찰도 완료 기준에 포함하므로, 관찰 대기나 미달을 구현 성공으로 대신하지 않는다. 40일 상한 안에 범위를 담기 어렵다면 사용자와 재협상한다.

## 첫 핵심 흐름와 소요 측정

첫 핵심 흐름(우선순위 1)은 **가입 → 프로젝트 → 게시 → 피드/프로젝트 타임라인 동시 반영 → 공유 URL**이다 [확정, 사용자 2026-09-27; KR1]. [전략 §4](../insight-strategy.md#4-검증-우선순위-순서-강제-아님)의 검증 단위이며 다른 독립 작업의 준비·진행을 막지 않는다. 구현 이슈를 만들 때 다음 항목을 함께 기록한다(K-3·KR4).

[제안, K-10] 커스텀 도메인 없이 준비하는 [로그인 절차](../research/oauth-login-check.md)는 문서 확인 완료·사용자 실행 대기이며 실제 결과는 미기록이다([기술 §3 공식 확인](../03_TECH_SPEC.md#인증-방식과-구현안), 2026-09-27 00:23~00:24 KST). 예산 상한 80시간 대비 완료 판단은 실제 투입 시간 측정과 핵심 흐름·이벤트 검증 뒤 수행한다.

| 측정 항목 | 기록 기준 [확정, 사용자 2026-09-27] | 현재 값 |
|---|---|---|
| 시작·완료 시각 | 구현 착수와 연결 흐름·행동 이벤트 검증을 마친 시각 | 미착수 / 미완료 |
| 실제 소요 | 작업 구간별 투입 시간을 합산하고 대기·중단 시간을 분리. 경과 시간과 실제 작업 시간을 구분 | [미정] |
| 가용 시간 기준 총 예산 | 사용자가 정한 하루 가용 시간과 최대 40일 안의 실제 작업 가능일로 산정. 가용 시간이 다르면 일별로 합산 | 상한 80시간 = 하루 2시간 × 최대 40일 [확정, 사용자 2026-09-27]. 실제 작업 가능일이 40일보다 적으면 그만큼 줄어든다 |
| 소요 비중 | 핵심 흐름 1의 누적 실제 투입 시간 ÷ 가용 시간 기준 총 예산. 총 예산 상한 80시간 기준 | 착수 전 0시간 / 80시간 |

완료 전에도 누적 소요를 확인하고 **핵심 흐름 1의 실제 투입 시간이 27시간을 넘으면 사용자에게 범위 재협상을 요청한다** [확정, 사용자 2026-09-27; KR4]. 총 예산 상한 80시간의 `1/3`을 약 27시간으로 잡았으며 실행 판단은 **27시간 초과**로 통일한다. 재협상 후보는 **소스 4개 → 1개, 카드 템플릿 3종 → 1종, 관리자 편의 기능** 순서로 확정했다. 후보를 자동 축소 결정으로 간주하지 않으며 지도·결제·RSS/AI 자체는 후보에 넣지 않는다. 기존 조정 원칙과 40일 상한을 유지한다.

이벤트 5개의 실제 기록·데모/운영자 제외(KR5)와 정직성 자동 검사 3개(KR3)의 통과 증거가 없으면 1차 프로토타입을 완료로 인정하지 않는다 [확정, 사용자 2026-09-27]. 기록·제외·권한·정리·자동 검사 범위는 [기술 명세 §8·§9](../03_TECH_SPEC.md#행동-이벤트)를 따른다.

## 일정이 부족할 때의 조정 원칙

인기 점수·개인화·추가 유료 상품·SNS 공유 이미지·네이티브 앱은 이미 이후 범위다. 외부 수집과 AI 원고는 사용자가 MVP로 선택했으므로 내부 템플릿만으로 대체하거나 조용히 뒤로 미루지 않는다. 수집 소스 수·카드 템플릿·관리자 화면의 편의 기능부터 줄이는 방안을 검토하고, 핵심 범위 조정이 필요하면 사용자에게 알린다. 지도·결제·취소·내역과 필수 검증도 제외하지 않는다.
