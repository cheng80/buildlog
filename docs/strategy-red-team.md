## 1. 상위 공격 가설

### K-1. 제작자 보상 루프 없이도 두 번째 게시가 일어난다

- **주장**: S-1은 "첫 게시까지의 마찰"을 제1 지표로 삼고, S-4는 카드 반응 숫자 숨김을 브랜드 자산으로 승격한다. 두 가설은 함께 "게시가 쉬우면 제작자는 계속 올린다"를 전제한다.
- **가장 강한 형태**: 사용자 원문 "쉽게 올릴 수 있어야 하고 외부 영상 링크도 쉽게"는 마찰이 실제 장벽임을 말한다. 유튜브 devlog 제작자는 이미 콘텐츠를 만들고 있어 붙여넣기만 하면 된다. 숫자 숨김은 초기 소규모 상태를 방어한다.
- **공격**: 마찰은 첫 게시를 설명하지만 두 번째 게시를 설명하지 않는다. Q3로 댓글·별도 알림함·개발자 팔로우가 빠지고 카드 숫자가 숨겨졌다. 제작자가 게시 후 받을 수 있는 신호는 팔로잉 피드에 자기 글이 뜨는 것과, 명세가 아직 정하지 않은 "본인 글의 좋아요 수 열람"뿐이다. 제품 명세 FR-007은 "기본 카드에서 숨긴다"고만 했고 **작성자 본인이 자기 글의 반응을 볼 수 있는지는 어디에도 없다**. 보상이 0인 SNS에서 연재는 일어나지 않는다. 마찰 감소는 필요조건이고 보상은 충분조건인데, 전략은 필요조건만 다룬다.
- **Fails if**: 인터뷰한 제작자 다수가 기존 채널에서 devlog 연재를 멈춘 이유로 "쓸 시간·수고"가 아니라 "반응이 없어서·의미가 없어서"를 꼽는다.
- **이번 주 확인할 증거**: 디스콰이엇 메이커로그·유튜브 devlog·GeekNews Show GN에 최근 6개월 내 글을 올린 제작자 5명에게 세 질문. ① 어디에 올렸고 왜 멈췄나 ② 내 글 반응 숫자를 못 보면 올릴 것인가 ③ 카드에서 숫자를 숨기고 본인만 보는 방식이면 어떤가.
- **이번 주 확인할 증거 — 대체 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: [공개 관찰 보고서](research/creator-loop-observation.md)의 공개 프로젝트별 후속 게시 유무·게시 간격·공개 반응을 확인한다. 동기나 비공개 본인 통계 필요성은 관찰 불가로 남긴다.
- **중단 기준(제안)**: 5명 중 3명 이상이 ②에 "안 올린다"고 답하면, "본인 통계 열람"을 MVP 결정 항목으로 승격한다. 카드 숫자 숨김(Q3)은 유지 가능하므로 확정 결정과 충돌하지 않는다. 다수가 댓글·알림까지 요구하면 **Q3·ADR-0003과 충돌**하므로 재검토 사유와 함께 사용자에게 올린다.
- **중단 기준 — 대체 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: 후속 게시와 공개 반응의 동반 여부만 보고 "반응 부족 때문에 중단" 판정을 보류한다. 본인 통계 제공 여부·범위는 관찰 한계를 붙여 해당 구현 이슈 착수 전 제품 질문으로 제출하고 기존 인원 임계값은 적용하지 않는다.
- **가장 싼 실험**: 인터뷰 5건. 구현 0. 인터뷰가 어려우면 명세에 "작성자 본인은 자기 게시물·프로젝트의 좋아요·저장·팔로우 수를 본다"를 결정 항목으로 추가하는 것만으로도 하중을 줄인다.
- **반영 상태(2026-09-26)**: [제안] [공개 관찰 B1·B2](research/creator-loop-observation.md)에서 30건·24개 제작자 핸들·30개 프로젝트를 확인했으나 같은 프로젝트의 후속 게시는 표본 안에 없었다([최신 목록](https://itch.io/devlogs/most-recent), 2026-09-26 22:48:43 KST). 정성 자료 6건은 원문 확인 2건·검색 발췌만 4건으로, 제작 수고·낮은 반응의 인과나 본인 통계 필요성은 확정할 수 없다(확인 URL·시각은 B2 각 행, 2026-09-26 22:47~22:50:50 KST). **중단 기준: 판정 불가·근거 부족.** 기존 인터뷰 인원 기준은 적용 불가이며 본인 통계 필요성의 관찰 판정과 제공 정책은 구분한다. 본인 게시물·프로젝트의 좋아요 수·저장 수·프로젝트 팔로우 수를 본인만 보는 화면에 제공하는 Q19를 확정해 K-1 결정 의존성을 해소했다 [확정, 사용자 2026-09-26]. 재시도 보완 [제안]: [Reddit R3~R6의 원문 확보 실패](research/creator-loop-observation.md#재시도-보완-2026-09-26)로 B2의 원문 2건·발췌 4건과 R6 게시일 미확인, B2·B6의 정성 서열을 유지하며 Q19 제공 결정과 효과 미검증을 구분한다(확인 URL은 보고서 H2 각 행, 2026-09-26 23:30:18~23:34:11 KST).

### K-2. 검증 지표를 측정할 수 있다

- **주장**: S-1~S-8은 모두 행동 지표(첫 게시 도달, 게시 → 프로젝트 열람, referrer, 원문 클릭, 결제 → 시작 전환)로 검증한다.
- **가장 강한 형태**: 제품 명세 §2가 이미 같은 지표를 제안했고, 데모·운영자 활동은 별도 집계한다고 명시했다. 의도는 일관된다.
- **공격**: 기술 명세 §8의 관측 항목은 게시 실패·업로드 실패·미리보기 실패율·결제 불일치 같은 **실패율**뿐이다. 행동 이벤트(열람·클릭·전환)를 어디에 기록하고, 데모·운영자를 어떻게 제외하고, 비회원 세션을 어떻게 잇는지에 대한 설계가 문서 어디에도 없다. 분석 도구 선택도 없다. 측정 수단이 없는 가설은 검증 불가이고, 검증 불가한 가설은 40일이 끝나도 참·거짓을 모른다. 전략 문서 전체가 이 한 공백에 걸려 있다.
- **Fails if**: 첫 핵심 흐름가 배포되는 시점까지 행동 이벤트 기록 방식이 정해지지 않는다.

- **가장 강한 형태**: 타입이 다르면 렌더 컴포넌트도 달라진다. 상태가 분리되면 "결제 완료"를 성급히 쓸 수 없다. 구조가 실수를 막는다는 관찰은 옳다.
- **공격**: I-12가 말하듯 개발자는 한 사람이다. **리뷰어가 없다.** 코드 리뷰를 집행 장치로 두면 집행자가 0명이다. 또 타입은 서버 응답을 구분할 뿐, 화면에서 `official_card`를 `user_post`와 같은 모양으로 그리거나 배지를 빼는 것은 타입이 막지 못한다. 반응 숫자 숨김(Q3)도 데이터가 아니라 렌더 결정이다. 구조가 막는 것은 "데이터 위조"이고 막지 못하는 것은 "표시 누락"이며, S-4의 실패 경로 대부분은 후자다.
- **Fails if**: 배지 유무·반응 숫자 미표시·광고의 자연 피드 미혼입을 검사하는 자동 단언이 우선순위 2 핵심 흐름의 완료 조건에 없다.
- **이번 주 확인할 증거**: 기술 §9 검증 계약에 위 세 단언이 있는가. 현재는 "카드 입력 검증"만 있고 표시 규칙 단언은 없다.

Q19 본인 화면 통계를 기본 카드 숫자 숨김 단언과 분리해 검증하며 기존 세 단언의 구현·통과 증거는 남아 있다. **PRD 채택 반영(2026-09-27):** KR3의 공식/데모/광고 배지·기본 카드 반응 숫자 없음·광고의 자연 피드 제외 자동 검사 3개를 1차 프로토타입 완료 조건으로 확정했으며 실제 통과 증거는 미확인이다 [확정, 사용자 2026-09-27].

### K-11. 운영자 자체 devlog가 실사용 예시가 된다

- **주장**: I-12와 S-3은 BuildLog 자체 프로젝트의 실제 개발 게시가 가장 설득력 있는 사용 예시이자 첫 실사용 검증이라고 본다.
- **가장 강한 형태**: 만든 사람이 직접 쓰면 게시 마찰을 몸으로 확인한다. 콘텐츠도 생긴다. 외부 의존 0이고 K-7의 2주 실험으로 지속 가능성까지 본다.
- **공격**: 첫째, 기술 §8은 운영자 활동을 `is_operator`로 실제 사용자 지표에서 제외한다. 자체 devlog는 **설계상 측정 신호가 0**이다. 둘째, 출시 시점 피드는 운영자 1명의 글 + 데모 3개 + 공식 카드로, 방문자 눈에는 한 사람이 운영하는 사이트다. "죽어 보이면 안 된다"는 사용자 원문이 겨냥한 상태와 같다. 셋째, 만든 사람의 직접 사용 검증은 모르는 사람의 마찰을 드러내지 못한다. 온보딩 3단계를 이미 아는 사람이 온보딩을 검증할 수 없다.
- **Fails if**: 핵심 흐름 1 배포 후 2주 안에 운영자 외 제작자의 게시가 0건이다.
- **이번 주 확인할 증거**: K-1 인터뷰 대상 5명 중 배포 후 첫 게시를 해 줄 사람이 있는가.
- **이번 주 확인할 증거 — 대체 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: `docs/research/creator-loop-observation.md`의 운영자와 구분 가능한 공개 제작자 게시·연재 사례를 확인하고, 빌드로그 배포 후에는 실제 외부 제작자의 첫 게시·후속 게시를 별도 기록한다. 타 서비스 관찰은 빌드로그 참여 약속이 아니다.
- **중단 기준(제안)**: 5명 중 1명도 "배포되면 올려 보겠다"가 없으면 S-3의 자체 devlog는 "콘텐츠"로만 두고 "검증" 역할을 뺀다. 첫 외부 제작자 확보를 S-1 검증의 선행 조건으로 올린다.
- **중단 기준 — 대체 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: 실제 외부 제작자 행동이 확인되기 전까지 운영자 자체 게시를 S-1의 외부 사용자 검증으로 인정하지 않는다. 공개 관찰은 연재 사례 참고로만 사용하며 인터뷰 참여 의향 임계값은 적용하지 않는다.
- **가장 싼 실험**: K-7의 2주 devlog 실험은 그대로 두고, K-1 인터뷰 끝에 "배포되면 첫 게시를 부탁해도 되는가" 한 문장을 추가한다. 구현 0.

### K-5. 하루 최대 2개 소식 카드가 2차 타깃의 재방문 이유가 된다

- **주장**: S-6은 인디 뉴스·포럼 카드가 비제작자의 재방문 이유이며, 그 방문자가 프로젝트를 팔로우해 제작자에게 돌아간다고 본다.
- **가장 강한 형태**: 사용자가 권장안보다 범위를 넓혀 확정한 영역이다(Q5). 소스 4개의 수집 경로가 실제로 확인됐다. 큐레이션 수요는 GeekNews의 존재 자체가 증명한다.
- **공격**: 바로 그 GeekNews가 문제다. GeekNews는 이미 한국어 요약을 하루 수십 건 낸다. 빌드로그의 소식 카드는 Q8 상한으로 하루 최대 2개이고, 소스 4개 중 GeekNews를 뺀 3개는 영어 원문이다. GeekNews 소재를 다시 요약하면 가치가 없고, 영어 소재를 요약하면 GeekNews와 경쟁한다. 하루 2개로 "매일 올 이유"가 되기는 어렵다. 또한 "소식 카드 방문자가 프로젝트를 팔로우한다"는 인과는 두 단계 건너뛴다. 이 공격은 범위를 빼라는 것이 아니다. **기대 역할을 낮추라**는 것이다. 소식 카드는 재방문 유인이 아니라 피드 채움 보조로 두는 편이 정직하다.
- **Fails if**: 1주 수동 수집에서 "인디 개발·메이커" 적합 소재가 하루 2개에 못 미치거나, 적합 소재의 대부분이 이미 GeekNews에 한국어로 올라와 있다.
- **이번 주 확인할 증거**: 확인된 소스 4개의 피드를 7일간 하루 한 번 수동으로 열어 스프레드시트에 기록한다. 항목: 제목, 소스, 인디 적합 여부, GeekNews 중복 여부. 구현 0.
- **중단 기준(제안)**: 7일 중 4일 이상 적합 소재가 2개 미달이면 일간 카드 대신 **주간 다이제스트 1장**(Q8 상한 안에서 가능)으로 재구성을 검토한다. 중복률이 높으면 GeekNews를 소스에서 빼고 영어 소스의 한국어 소개에 집중한다.
- **가장 싼 실험**: 위 7일 스프레드시트. 이 데이터는 나중에 허용 소스 목록 결정(PLAN-001 후속)에도 그대로 쓰인다.
- **반영 상태(2026-09-26)**: [제안] [1일차 스냅샷](research/source-sample/2026-09-26.md)에서 4개 경로·item 조회 모두 HTTP 200, 제공순 표본 80건 중 적합 45건·부적합 34건·보류 1건을 기록했다(확인 URL·시각은 보고서 HTTP/항목 표, 2026-09-26 22:48:25~22:48:27 KST). 당일 적합 28건은 중복 미확인을 포함하며 서로 다른 제작 도구 2건으로 1일차 공급 기준은 충족한다. **7일 중단 기준: 판정 불가·근거 부족.** 나머지 6일은 미수집이고, 발행시각 기준 최신 20건·GeekNews 전체 중복도 미확인이라 관찰만으로 카드 형식·재방문 효과를 확정하지 않는다. 초기 허용 소스는 별도 사용자 결정(Q15)으로 확정했다 [확정, 사용자 2026-09-26]. ### K-12. 조작 지점은 게시 빈도뿐이고 429가 막는다

- **주장**: I-13은 순위가 전부 `published_at` 파생값이라 조작 가능한 지점은 게시 빈도뿐이며 429 한 곳에서 방어된다고 본다. S-2 실행 방향이 이를 받았다.
- **가장 강한 형태**: 수동 순위 필드가 없으니 "상단 고정" 요청이 들어올 자리가 없다. 규칙이 하나라 설명이 필요 없고, 활동 점수 없이도 정직하다.
- **공격**: 429는 요청 빈도 제한이지 하루 게시 상한이 아니고 임계값도 미정이다. 성실한 다작 제작자가 하루 10건을 올리면 최신순 피드는 그 사람 것이 된다. 스팸이 아니라 신고 대상도 아니다. 파생 규칙은 정직하지만 "한 업데이트를 잘게 쪼개 올리기"라는 **정직한 퇴화 전략**을 허용한다. Release도 게시물이라 Release마다 재노출이 생긴다. K-4가 이미 "제작자 3명이 화면 대부분"을 짚었는데, 재독 갱신은 이를 "429 한 곳에서 방어"로 낙관했다.
- **Fails if**: 데모 20건·제작자 3명 분포 목업에서 한 제작자가 화면 절반 이상을 차지한다.
- **이번 주 확인할 증거**: K-4의 목업 스크린샷. 이미 계획된 실험이다.
- **중단 기준(제안)**: 목업에서 독점이 보이면 "피드에서 같은 프로젝트의 연속 카드 접기" 같은 표시 규칙을 사용자에게 제안한다. 이는 Q4(최신순)를 바꾸지 않는 표시 결정이지만 제품 결정이므로 개발자가 단독으로 정하지 않는다.
- **가장 싼 실험**: K-4 목업에 "한 제작자 하루 10건" 케이스 한 장 추가. 비용 10분.
- **반영 상태(2026-09-26)**: [제안] [경쟁 관찰 §4의 허구 목업](research/competitor-check.md)을 대조했다(로컬 검토 2026-09-26 23:07:58 KST). 균등 케이스 A는 첫 10건의 최대 점유 4/10(40%)으로 **중단 기준 미충족**, 집중 케이스 B는 10/10(100%)으로 **중단 기준 충족**이다. 실제 이용자·실기기 화면·429 통과 결과가 아니며, 같은 프로젝트 연속 카드 접기 표시 규칙의 판단 근거로 사용했다. 전체·팔로잉 자연 피드에서 동일 프로젝트 연속 2건 이상은 최신 1장과 펼치기로 표시하고 접힌 Release 안내·원래 위치/최신순·타임라인 전체 기록·공식/광고 제외를 유지하며 페이지 응답 안 접기는 [기본값 제안]으로 채택했다 [확정, 사용자 2026-09-26].

### K-14. 미정은 전부 자원이므로 다시 묻지 않는다

- **주장**: I-11은 확정은 제품 규칙, 미정은 시간·돈·사람·계약이며 자원 미정을 제품 미정으로 오해해 재질문하지 않는다고 본다.
- **가장 강한 형태**: Q1~Q14가 제품 동작을 덮었고 남은 것은 모델·예산·시간·도메인이다. 이 구분이 §4 착수 판단을 단순하게 만든다. 이미 받은 승인을 반복 확인하지 않는다는 저장소 규칙과도 맞는다.
- **공격**: "자원"으로 분류된 미정 중 일부는 제품 결정이다. **허용 소스 목록**은 피드에 무엇이 보이는지 정한다. **광고 슬롯 수**는 화면의 몇 퍼센트가 광고인지 정한다. **데모 프로젝트 수·교체 주기**는 초기 피드의 절반을 정한다. **운영자 지정**은 누가 글을 숨길 수 있는지 정한다. 이 넷을 자원으로 두고 "다시 묻지 않는다"를 적용하면 개발자가 구현 이슈 안에서 제품 결정을 혼자 내리게 되고, "제품의 선택은 사용자 답변으로 확정한다"는 PLAN-001 §1 원칙과 충돌한다.
- **Fails if**: PLAN-001 §5 "구현 전에 정할 항목" 표를 자원/제품으로 나눴을 때 3개 이상이 제품이다.
- **이번 주 확인할 증거**: 표 한 번 분류. 15분.
- **중단 기준(제안)**: 제품으로 분류된 항목은 해당 구현 이슈 착수 전 Q15 이후 번호로 사용자에게 묻는다. I-11의 "다시 묻지 않는다"는 "이미 답한 Q1~Q14를 다시 묻지 않는다"로 좁힌다.
- **가장 싼 실험**: 분류 표. 구현 0.
- **후속 반영(2026-09-26) [제안]**: PLAN-001 §5에 자원/제품 성격 열을 추가하고 제품 미정은 §9의 Q15 이후 질문·권장안·영향 초안으로 연결했다. 당시 구현 이슈 착수 전 제출할 준비안이었으며 현재는 §9 확정 답변으로 갱신했다. Q15~Q24 권장안 채택으로 제품 판단을 종결하고 확정 원칙과 변경 가능한 기본값을 구분했으며 자원 준비·7일 관찰은 별도로 남긴다 [확정, 사용자 2026-09-26].

## 2. 하위 공격 가설 (짧게)

### K-6. 제작자가 프로젝트 URL을 외부에 공유한다 (S-5)

- **공격**: 제작자에게는 이미 GitHub README, 유튜브 채널, 노션이 있다. 빌드로그 링크를 하나 더 넣을 이유는 프로젝트 페이지가 그것들보다 나을 때만 생긴다. 공유 이미지 자동 생성은 이후 범위라 링크 미리보기는 대표 이미지 한 장이다.
- **Fails if**: 인터뷰에서 다수가 "README·노션으로 충분"이라 답한다.
- **가장 싼 실험**: K-1 인터뷰에 질문 하나 추가. "이 프로젝트 페이지(소개 사이트 목업)를 README 상단에 넣겠는가, 왜."
- **이번 주 확인할 증거 — 대체 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: `docs/research/creator-loop-observation.md`에서 공개 README·프로젝트 소개·영상 설명의 개발 기록 링크와 새 게시물 공유 링크를 기록한다. 실제 공유 의향이나 빌드로그 링크 선택 여부는 미확인이다.
- **중단 기준(제안)**: 5명 중 3명 이상 "안 넣는다"면 S-5를 성장 채널에서 빼고, 유입 채널 가설을 새로 세운다.
- **중단 기준 — 대체 [제안]**: 인터뷰 기반 기준은 적용 불가. 대체 관찰: 공개 링크의 존재·부재를 기록하되 부재를 공유 거절로 간주하지 않는다. S-5는 실제 유입 기록이 생길 때까지 가설로 두고 기존 인원 임계값으로 제외하지 않는다.
- **반영 상태(2026-09-26)**: [제안] [공개 관찰 B3](research/creator-loop-observation.md)에서 대표 링크 목적지는 자체 사이트 8건·GitHub README 3건·플랫폼 프로젝트 페이지 5건이었다(표본 16개; 확인 URL·시각은 B3 각 행, 2026-09-26 22:48:43~22:52 KST). 플랫폼 탐색 링크와 제작자의 외부 공유 선택을 구분하며, 링크 존재로 빌드로그 URL 공유 의향·유입·가입을 추정하지 않는다. **중단 기준: 판정 불가·근거 부족.** 기존 인터뷰 인원 기준은 적용 불가이며 S-5는 가설로 유지한다. Q19 본인 통계와 Q21 소개 문구가 확정돼도 외부 공유 의향·성장 효과의 관찰 공백은 남는다. 재시도 보완 [제안]: [Reddit 원문 4건 재확인 실패](research/creator-loop-observation.md#재시도-보완-2026-09-26)로 B2 분류·B6의 제품 문제 4개 직접 언급 0건 및 동률·보류 서열은 바뀌지 않았으며, 콘텐츠 제작 수고의 인접 근거를 빌드로그 URL 공유 의향이나 유입 효과로 확대하지 않는다(확인 URL은 보고서 H2 각 행, 2026-09-26 23:30:18~23:34:11 KST).

### K-7. 공식 카드·데모가 비회원 → 가입을 만든다 (S-3)

- **공격**: 가입 동기는 "내 프로젝트를 올릴 곳"이고 이는 피드 내용과 무관하다. 공식 카드와 데모는 이탈(bounce)을 막는 역할이지 가입을 만드는 역할이 아니다. S-3의 지표 "비회원 열람 → 가입"은 인과가 틀렸을 가능성이 크다. 더 큰 문제는 운영자다. 운영자 지정은 후속 결정이고, 현재 개발자 본인이 운영자라면 하루 검수·자체 devlog 연재·개발을 병행해야 한다.
- **Fails if**: 2주간 주 2회 자체 devlog를 못 쓴다.
- **가장 싼 실험**: 소개 사이트 저장소나 마크다운에 빌드로그 개발 devlog를 2주 연재해 본다. 지속되면 S-3의 "가장 설득력 있는 사용 예시"가 실체를 얻고, 안 되면 데모·만들기 주제 카드 위주로 축소한다.
- **지표 수정 제안**: "비회원 열람 → 가입" 대신 "비회원 피드 체류·두 번째 페이지 이동"으로 바꾼다. 가입은 S-1·S-5 지표에서 본다.
- **반영 상태(2026-09-26)**: S-3·FR-009에 반영 완료. K-11이 "실체를 얻는다"는 해석을 이어서 공격한다. Q17 데모 3개·필요 시 교체·좋아요/저장 허용·실사용자 집계 제외 및 Q18 사용자 본인 계정의 명시적 운영자 역할을 확정했다 [확정, 사용자 2026-09-26].

### K-8. Featured 테스트 결제가 수요 신호다 (S-7)

- **공격**: 실제 청구가 없는 1,000원 테스트 결제는 지불 의사를 측정하지 못한다. "노출 시작" 클릭은 호기심이다. S-7의 검증 지표는 기술 검증 지표로는 유효하지만 수요 신호로는 무효다.
- **결론**: 반박 성공. Featured MVP의 역할을 **과제 조건 충족 + 결제·취소·대사 파이프라인 기술 검증**으로 재분류한다. 실제 수요 신호가 필요하면 K-1 인터뷰에 "프로젝트 노출에 월 얼마까지 낼 것인가"를 넣거나, 가격 없는 관심 등록을 별도 실험으로 둔다.
- **비용**: insight-strategy.md S-7 한 줄 수정.
- **반영 상태(2026-09-26)**: S-7·FR-011 재분류 완료. 종결. Q16 광고·중복 구매·미시작 취소 정책 확정은 결제 기술 검증 범위를 구체화하며 수요 검증으로 확대하지 않는다 [확정, 사용자 2026-09-26].

### K-10. 우선순위 1~3은 자원 미정 없이 착수할 수 있다 (§4 선행 미정 열)

- **공격**: 핵심 흐름 1은 Supabase 프로젝트 생성, GitHub·Google OAuth 앱 등록, Vercel 프로젝트가 필요하다. OAuth 앱은 콜백 URL을 요구하고 도메인은 Q7 미정이다. Supabase Auth의 제공자 콜백은 Supabase 호스트로 가고 사이트 URL은 `*.vercel.app`로 둘 수 있어 막히지 않을 가능성이 높지만, 문서에 확인 기록이 없다. 또 K-3의 `1/3` 규칙은 총 예산이 있어야 계산되므로 핵심 흐름 1의 "예산 대비 판단"은 가용 시간 미정에 걸린다. "착수"는 가능해도 "완료 판단"은 미정에 걸린다.
- **Fails if**: 커스텀 도메인 없이 GitHub·Google 로그인이 동작하지 않는다.
- **가장 싼 실험**: 30분. Supabase 프로젝트와 GitHub OAuth 앱을 `*.vercel.app` 기준으로 만들어 로그인 한 번.
- **중단 기준(제안)**: 안 되면 §4 우선순위 1의 선행 미정에 "도메인 또는 임시 호스트 확정"을 추가한다. 되면 §4의 주장은 "착수 가능"으로 유지하되 "완료 판단은 K-3 후"를 덧붙인다.
- **후속 반영(2026-09-26) [제안]**: [기술 §3](03_TECH_SPEC.md#인증-방식과-구현안)에 공식 출처와 확인 시각을 기록했다. 문서상 커스텀 도메인 없이 착수 가능하나 실제 로그인은 미검증이며 예산 대비 완료 판단은 K-3 확정 후다. 계정 연결은 Q22의 Supabase Auth 기본 동작·임의 병합 금지·수동 UI 제외로 확정했으며 실제 로그인은 구현 시 검증한다 [확정, 사용자 2026-09-26]. **2026-09-27 추가 반영:** [공식 확인표·로그인 체크리스트](research/oauth-login-check.md) 준비 완료, 사용자 실행 대기·결과 미기록이며 제공자별 성공 기록 전에는 K-10 통과로 판정하지 않는다(공식 URL·확인 시각은 보고서, 2026-09-27 00:23~00:26 KST).

## 3. 잘 세워진 것

의심을 제조하지 않기 위해 명시한다.

- **프로젝트 필수 연결(ADR-0001)**: "개발과 무관한 게시물" 필터를 규칙 하나로 얻는다. 스팸 방어이자 구조 일관성이다. 공격할 지점이 없다.
- **정직성 규칙 자체(BR-005/006/011/013)**: 가짜 수치·후기·가격 금지는 기본 기능으로서 옳다. 공격한 것은 이를 "성장 자산"으로 부르는 해석(S-4)이며, 규칙은 유지한다.
- **과제 조건 격리(I-6)**: 지도는 시·군·구 대표 좌표만, 결제는 상품 하나·수동 시작. 핵심 루프를 잠식하지 않게 설계했다. 사용자 원문("예약은 하고 싶지 않다")과도 일치한다.
- **자동화의 방어선**: 승인 필수, 일일 상한, 비용 상한 미설정 시 비활성, 출처 URL 변경 금지, 원문 지시문 격리. 실행 여부와 별개로 설계는 튼튼하다.
- **결제 상태 분리(주문·결제·노출)와 대사**: 성공 URL을 완료로 보지 않고 확인 중 상태를 둔 것은 과제용 결제에서 흔히 빠지는 부분이다.
- **40일을 상한으로, 순서를 자유로 둔 것**: 리스크 순 검증(K-3의 핵심 흐름 측정)이 가능해진 근거다.
- **5:1 혼합 상한과 같은 카드 복제 금지**: 공식 카드가 피드를 덮는 실패 경로를 규칙으로 막았다.
- **파생값 원칙(I-13)**: 순위에 수동 필드가 없다는 관찰은 옳고 유지할 가치가 있다. 공격한 것은 "429로 충분"이라는 해석(K-12)뿐이다.
- **정직성의 구조화(I-14)**: 타입·상태 분리가 데이터 위조를 막는다는 관찰은 옳다. 공격한 것은 집행 장치를 코드 리뷰에 둔 것(K-13)이다.
- **자원/제품 분리(I-11)와 §4 선행 미정 열**: 착수 판단 도구로는 옳고 로드맵의 조건 표와 일치한다. 공격한 것은 경계선의 위치(K-14)와 완료 판단의 의존성(K-10)이다.
- **팔로잉 탭이 유일한 재방문 경로라는 관찰(I-15)**: 관찰 자체는 정확하고 측정 공백을 드러냈다. 공격한 것은 그 위에 세운 해결책의 인과(K-9)다.

## 4. 판단할 수 없었던 것

- **소개 사이트의 실제 반응**: buildlog-showcase가 공개된 상태인데 방문·문의 데이터가 이 저장소에 없다. 있다면 K-6·K-7·K-9의 가장 싼 증거다.
- **경쟁 서비스의 현재 기능**: [경쟁 관찰](research/competitor-check.md)에 직접 확인 기록을 남겼다(확인 URL·시각은 서비스별 표, 2026-09-26 22:39~22:42 KST). K-4의 재분류 권고 기준은 충족했으나 미확인 기능·로그인 후 동작·시장성은 판단하지 않았다. [제안]
- **문제별 중요도·만족도**: 제품 명세 §2의 문제 4개(긴 글 쓰기 어려움 / 맥락 유실 / 출시 후 재소개 어려움 / 볼거리 부족)에 대해 제작자가 얼마나 중요하게 느끼고 현재 수단에 얼마나 만족하는지 데이터가 없다. Opportunity Score를 계산할 수 없고, S-1~S-8이 어느 문제에 하중을 걸어야 하는지도 판단이다. K-1 인터뷰에 문제 4개 × (중요도 1~5, 현재 만족도 1~5) 두 문항을 넣으면 5명분이지만 첫 데이터가 생긴다. 5명은 통계가 아니라 방향 확인이다.

위 중요도·만족도 인터뷰안도 사용자 결정으로 적용 불가다. 공개 관찰은 보이는 행동만 기록하며 주관적 중요도·만족도나 Opportunity Score를 대신 계산하지 않는다. [미정]

## 5. 이번 주 할 일

초기 여섯 항목의 조사·결정 이력을 유지하고, 채택한 PRD에 따라 1차 프로토타입 착수 준비로 연결한다. 실제 앱 구현·검증은 아직 시작하지 않았다.

1. **공개 관찰 완료·행동 검증 대기** (K-1·K-6·K-8·K-9·K-11): [공개 관찰 보고서](research/creator-loop-observation.md)의 URL·KST 시각과 한계를 확인했다. 동기·본인 통계 필요성·공유 의향·지불 의사·재방문은 검증 완료가 아니며, 출시 후 실제 게시·열람 계측과 Q19 본인 통계의 효과를 검토한다. 인터뷰는 사용자 결정으로 불가하다. [제안]
2. **확정한 행동 이벤트 구현 준비** (K-2, K-9): 자체 `events`·Supabase Cron(`pg_cron`) 30일 정리·서버 발급 HttpOnly 쿠키 30분 절대 만료·SQL 뷰 1개와 관리자 페이지 1개를 적용하고 KR5 이벤트 5개를 1차 완료 전에 검증한다 [확정, 사용자 2026-09-27]. Q20 완전 준수는 권한·신원 분리·정리 지연/중지/백업 검증 뒤 판정하며, 팔로잉 탭과 개별 게시물 실제 열람의 추가 계측은 2차 후속이다.
3. **가용 시간·로그인 확인** (K-3, K-10): 하루 2시간·총 예산 상한 80시간은 확인 완료 [확정, 사용자 2026-09-27]. 핵심 흐름 1 이슈에 시작·완료·실제 소요를 기록하고 27시간 초과 시 범위 재협상을 요청한다 [확정, 사용자 2026-09-27]. [로그인 절차](research/oauth-login-check.md)는 준비 완료, 사용자 실행 대기·결과 미기록이며 두 제공자 결과를 따로 남긴다. 조작 약 29분은 계획 추정이고 설정 반영 대기를 포함한 30분 완료는 보장하지 않는다([Google 공식 안내](https://support.google.com/cloud/answer/15549257), 조사 확인 2026-09-27 00:26 KST).
4. **경쟁·목업 권고 채택 완료** (K-4, K-12): 재노출 기본 기능 재분류·연속 카드 접기를 확정했다 [확정, 사용자 2026-09-26]. [보고서](research/competitor-check.md)의 관찰 한계를 유지하고 정렬·타임라인 보존·펼치기·Release 안내를 구현 시 검증한다.
5. **소스 4개 7일 수동 수집** (K-5): [1일차](research/source-sample/2026-09-26.md) 기록 완료, 나머지 6일 미수집. 초기 허용 목록은 Q15 확정이며 최신 항목 선별·GeekNews 전체 비교 한계를 보완해 주간 다이제스트 채택을 관찰 후 판단한다. [제안]
6. **PRD 확정·1차 착수 준비** (K-1, K-2, K-3, K-4, K-12, K-13, K-14): 기존 Q1~Q24·D1~D11을 보존하고 [PRD](PRD-buildlog.md)의 A1~A5를 정본에 반영했다 [확정, 사용자 2026-09-27]. KR1~KR5·1/2/3차 단계·27시간 재협상·행동 기록 구성·정직성 자동 검사 3개의 1차 완료 조건을 적용한다. 사용자가 K-10 로그인 체크리스트를 실행한 뒤 핵심 흐름 1 이슈와 시작 시각을 준비하며, K-9 가정·실제 효과·앱 검증은 미확인으로 남긴다.

이 여섯 개가 끝나면 S-1~S-8 중 무엇이 살고 무엇이 죽는지 데이터 없이도 절반은 알 수 있다. 확정 결정(Q1~Q14, ADR-0001~0003)은 이 문서로 바뀌지 않는다. K-1·K-9가 댓글·알림 요구로 이어질 때만 Q3·ADR-0003 재검토를 사용자에게 명시적으로 올린다. K-12·K-14의 이번 제품 결정은 Q15~Q24 및 연속 카드 접기로 확정했으며 다시 묻지 않는다. 새 범위 변경만 별도 결정으로 관리한다.
