# 빌드로그(BuildLog) 서비스 기획 핸드오프 · Codex용

> 작성: 2026-09-17 · 작성 근거: `buildlog-showcase` 저장소의 기획 문서(`docs/01~04`, `DESIGN.md`), 공개된 소개 사이트 https://buildlog-showcase.vercel.app 의 화면·카피(`app/page.tsx`), 사용자의 ChatGPT 기획 대화 추출본(`_workspace/chatgpt-project-idea-2026-09-16.md`).
>
> 이 문서는 **실제 서비스 빌드로그**를 기획하기 위한 인수인계다. 소개 사이트(`buildlog-showcase`)의 작업 인수인계는 `HANDOFF.md`가 따로 맡는다. 실제 서비스 저장소(`buildlog`)가 생기면 이 파일을 그쪽으로 옮긴다.

## 0. Codex에게

- 목표: 아래 자료를 바탕으로 실제 서비스 빌드로그의 **기획 문서 묶음**을 만든다. 코드를 먼저 쓰지 않는다.
- 근거의 우선순위: ① 사용자가 직접 결정한 것(이 문서에서 **[결정]**) → ② 소개 사이트가 이미 공개적으로 약속한 것(3절) → ③ ChatGPT 대화에서 나온 제안(**[제안]**) → ④ 이 문서 작성자의 추정(**[추정]**). ③·④는 기획하면서 바꿔도 되지만 ①·②는 사용자 확인 없이 바꾸지 않는다.
- 사용자에게 묻는 말은 **한국어로만** 쓴다. 문서도 한국어. 코드 식별자·제품명은 원문 그대로.
- 모르는 것은 지어내지 않는다. 숫자(사용자 수, 가격 등)는 근거가 없으면 쓰지 않는다.
- 다른 서비스(인스타그램, Product Hunt 등)는 참고 UX로만 언급하고, 사용자에게 보이는 문구에서는 비교하지 않는다.

## 2. 서비스 구조 (3층) — 정본

```text
개발자(프로필)
 ├─ 프로젝트 A   ← 상시 페이지: 소개·스크린샷·사용 기술·링크·Release·타임라인
 └─ 프로젝트 B
        ▲
   게시물은 반드시 프로젝트 하나에 연결

  [게시물] 스크린샷 / GIF / 유튜브·쇼츠 URL / GitHub URL / 웹사이트 URL + 한 줄
      │
 ┌────┴────┐
 ▼         ▼
피드       프로젝트 타임라인
(발견)     (기록·포트폴리오. 올릴 때마다 프로젝트가 피드에 재노출)

피드 = 사용자 게시물 + 공식 카드(오늘의 만들기 주제 / 개발 팁·기술 소식 카드뉴스 / 이번 주 프로젝트)
     → 사용자가 적어도 피드가 비지 않는다
```

| 층 | 무엇 | 사용자 말 (원문) | 상태 |
|---|---|---|---|
| 1. 가볍게 올리기 | 입력창 하나. URL을 붙이면 영상·저장소·링크 카드가 자동으로 된다. 글을 길게 쓰지 않는다. | "쉽게 올릴 수 있어야 하고 외부 영상 링크도 쉽게. 유튜브 영상로그 만드는 사람이 많다" | **[결정]** |
| 2. 프로젝트에 쌓이기 | 게시물과 Release가 프로젝트 타임라인에 누적. 새 기록을 올릴 때마다 프로젝트가 피드에 다시 뜬다. 출시는 이벤트가 아니라 주기. | "개발로그 연재 시 상위 노출" | **[결정]** — 국내 차별점 |
| 3. 피드가 안 죽기 | 공식·자동 생성 카드가 사용자 게시물 사이를 채운다. 데모 프로젝트는 데모라고 표시한다. | "게시물이 적어도 죽어가는 느낌이 들어선 안 된다" | **[결정]** — 카드뉴스 자동화 파이프라인을 요구 |

## 3. 소개 사이트가 이미 약속한 것 (실제 서비스가 지켜야 할 최소 기능)

소개 사이트는 "이미 운영 중인 서비스" 톤으로 공개돼 있다. 아래는 화면과 카피가 방문자에게 약속한 내용이며, 실제 서비스의 MVP는 이것을 깨지 않아야 한다. 출처: `docs/01_PRODUCT_SPEC.md` 4절, `app/page.tsx`.

### 3.1 올리기

| 입력 | 결과 |
|---|---|
| 스크린샷, GIF 업로드 | 이미지 게시물 (1:1 표시) |
| 유튜브·쇼츠 링크 | 영상 카드 (썸네일 + 재생 표시 + 길이) |
| GitHub 링크 | 저장소 카드 |
| 웹사이트 링크 | 링크 미리보기 |

- 입력창은 하나. 힌트 "오늘 뭘 만들었나요?". 한 줄 텍스트 + 붙여넣기(이미지·링크) + 프로젝트 선택 칩("작은 타이머") + 게시 버튼.
- 게시물은 프로젝트 하나에 반드시 연결된다. 같은 게시물이 피드와 프로젝트 타임라인 양쪽에 나타난다.
- "새로 만드는 게 아니라 이미 만든 것을 가져오는 방식"(FAQ). 유튜브에 올려 둔 개발 영상도 링크만으로 게시물이 된다.

### 3.2 피드

- 여러 개발자의 새 게시물이 한 피드에 흐른다. 피드는 **개발 중인 프로젝트 게시물로만** 채워진다(일상 글 없음).
- 사용자 게시물 사이에 공식 카드가 섞인다. 공식 카드 3종:
  - **오늘의 만들기 주제** — 무엇을 올릴지 알려 주는 카드 (예: "이번 주 가장 많이 바뀐 화면은 무엇인가요? 바꾸기 전과 후 화면을 나란히 올려 보세요.")
  - **개발 팁과 기술 소식** — 짧은 카드뉴스
  - **이번 주 프로젝트** — 올라온 프로젝트를 다시 소개
- 게시물 카드 구성: 아바타·이름·핸들(@handle) / 이미지 또는 영상 / 하트·말풍선·보내기·저장 아이콘 / 캡션 한 줄 / 연결된 프로젝트 이름·버전 칩. 소개 사이트는 숫자(좋아요 수 등)를 표시하지 않았으므로, 숫자 노출 여부는 실제 서비스에서 결정한다. **[추정]**

### 3.3 프로젝트 페이지

- 프로젝트마다 상시 페이지: 이름, 버전(예 v0.6), 한 줄 소개, 제작자, **사용한 기술 칩**(예 Flutter, Supabase), **링크**(GitHub, 웹사이트), **스크린샷** 여러 장, **개발 기록(타임라인)**.
- 타임라인 항목 종류: 이미지 게시물 / 영상 게시물 / Release(버전 공개, "Release" 태그). 날짜순.
- "새 기록을 올릴 때마다 프로젝트가 피드에 다시 나타난다." "이 페이지 링크 하나로 프로젝트 전체를 소개할 수 있다."(공유 가능한 공개 URL)

### 3.4 프로필·상호작용

- 개발자 프로필이 프로젝트 여러 개를 소유한다(계정은 개발자 단위, 프로젝트 단위가 아니다). **[결정]**
- 좋아요·저장·팔로우: "마음에 드는 프로젝트의 다음 기록을 놓치지 않습니다." (팔로우 대상이 개발자인지 프로젝트인지는 미정 — 5절)
- 소규모 개발팀·개발사도 대상: "팀 프로젝트의 진행 과정을 링크 하나로."

### 3.5 시작 3단계 (온보딩 순서)

1. 프로젝트 페이지 만들기 — 이름, 한 줄 소개, 사용한 기술.
2. 오늘 만든 것 올리기 — 스크린샷이나 유튜브 링크 + 한 줄. 피드와 프로젝트 페이지에 함께 올라간다.
3. 페이지 링크 공유하기.

### 3.6 타깃

| 사용자 | 원하는 것 |
|---|---|
| 1차: 혼자 만드는 인디 개발자 | 오늘 만든 화면 한 장으로 프로젝트를 꾸준히 알리기 |
| 1차: 소규모 개발팀·개발사 | 팀 프로젝트 진행 과정을 링크 하나로 보여주기 |
| 2차: 새 앱·게임을 찾는 사람, 동료 개발자 | 완성 전의 프로젝트를 먼저 구경하고 응원하기 |

### 3.7 FAQ에서 한 약속

- 완성 전이라도 앱·웹·게임 프로젝트면 올릴 수 있다.
- 글을 길게 쓰지 않아도 된다(스크린샷 한 장 + 한 줄).
- 유튜브 개발 영상 링크가 그대로 게시물이 되고 타임라인에도 남는다.
- 게시물이 흘러가 버리지 않고 프로젝트 페이지에 순서대로 쌓인다.

## 4. ChatGPT 기획 대화에서 나온 결정·제안·보류

출처: `_workspace/chatgpt-project-idea-2026-09-16.md`(4,502줄, 사용자 발화 19회). 대화는 여행·예약형 아이디어 거부 → Google Play 테스터 모집 플랫폼 검토·철회 → 인디 런칭 서비스 리서치 → "국내 차별점 + 개발로그 연재 시 상위 노출" → "인스타그램 같은 방향" → "게시물 적어도 죽어 보이면 안 됨" → 카드뉴스 자동화 → 쉬운 게시·유튜브 링크 → 소개 사이트와 실제 서비스 분리 순서로 흘렀다. ChatGPT의 「기획 요약」은 사용자가 "Product Hunt 비교 문구" 한 줄만 거부하고 이의 없이 넘어갔으므로 아래 **[제안]** 중 그 요약에 든 항목은 사실상 수용된 것으로 봐도 된다.

### 4.1 전제 조건 **[결정]**

- 실제 서비스는 **과제이기도 하다.** 필수 요소: 로그인/회원가입, CRUD 최소 1개, 지도/위치, 결제·결제취소·결제내역, 40일간 점진적 업그레이드. 나머지는 자유. "실제 상품이라 생각하고 기획".
- 포트폴리오용이 아니라 실제로 쓸 수 있어야 하고, 유료화가 붙어도 "단순 취지용"이면 된다. "재미와 눈으로 보이는 부분이 풍성한" 것. 예약·실시간 매칭·커뮤니티 활성화에 의존하지 않는다. 실제 유저가 없어도 더미 데이터로 채워져 보여야 한다.
- 결제는 단순해야 한다(예약형 흐름은 작업량·예외가 많아 회피).
- 지도/위치는 개발사 주소·소개 페이지 정보에 붙이는 정도로 끝낸다. 핵심 흐름에 넣지 않는다.
- 작업 순서: 서비스 핵심 기획 확정 → 소개 사이트 기획·제작(완료) → 이후 40일간 본 서비스 개발.

### 4.2 정의·차별점

- **[결정]** 국내 서비스로서의 차별점이 우선. "개발로그 연재 시 상위 노출" 같은 장치를 붙인다.
- **[결정]** 정의 문구는 3~5단어 안에 핵심이 담겨야 하고, 다른 서비스와 비교하는 설명은 금지.
- **[제안]** 문구 후보: "만드는 과정을 올리세요. 그 기록이 프로젝트의 홍보가 됩니다." / "개발 기록이 프로젝트 홍보가 된다" / "개발 과정을 공유하는 프로젝트 SNS"(소개 사이트가 채택).
- **[제안]** 기존 런칭 서비스는 완성 → Launch → 며칠 노출 → 종료. 빌드로그는 아이디어 등록 → 개발로그 → 재노출 → Beta → Release → 재노출 → 업데이트 → 재노출. **Launch는 이벤트가 아니라 lifecycle.** 국내 유사 서비스(디스콰이엇의 메이커로그, zero launch, Shift, GeekNews Show GN)가 있어 제품 등록·개발로그만으로는 차별화가 약하다. 재노출 규칙과 자동 콘텐츠가 차별점이다.
- **[제안]** 핵심 가치 4: 쉽게 기록 / 지속 노출 / 프로젝트 중심(게시물이 흘러가지 않고 누적) / 홍보 자동화(카드뉴스·공유 이미지로 재활용). 글 하나가 피드 + 프로젝트 타임라인 + SNS 공유 카드 + 포트폴리오 네 곳에 쓰인다. 원칙: "개발자가 콘텐츠를 새로 만들게 하지 말고, 이미 만들고 있는 것을 쉽게 가져오게 한다."

### 4.3 게시 (1층)

- **[결정]** 쉽게 올릴 수 있어야 하고 외부 영상 링크가 쉽게 붙어야 한다.
- **[제안]** 유형 선택 없이 입력창 하나. 필수 입력은 "내용" 하나, 이미지·링크·프로젝트·태그는 선택. 입력 자동 판별: 텍스트만 → 일반 개발로그 / 이미지 → 이미지 / GIF → 동작 미리보기 / YouTube URL → 영상 embed / Shorts URL → 세로형 영상 카드 / Vimeo → embed / GitHub URL → 저장소 카드(이름·스택·★·설명) / 앱스토어 URL → 앱 소개 카드 / 웹사이트 URL → OG 링크 카드. 영상은 서버 업로드 없이 URL 임베드.
- **[제안]** 내부 타입 `post: text / image / video_embed / link / release / project_update`. 사용자에게는 "게시물" 하나로 보이고 Release만 별도 액션.
- **[제안]** 게시물은 반드시 프로젝트에 연결. 최근 기록 기준으로 "이 게시물을 'X'에 연결할까요? [연결] [다른 프로젝트]" 자동 추천.
- **[제안]** 부가: 게시 후 "공유 카드 만들기"(SNS용 이미지 자동 생성), YouTube URL → 제목·썸네일·설명 자동 수집, 선택 실행 AI로 "개발로그 요약 만들기".

### 4.4 프로젝트 페이지 (2층)

- **[제안]** 프로젝트가 서비스의 중심. 필드: 대표 이미지, 소개, 스크린샷, Demo, 기술 스택, GitHub/Website 링크, 제작자, Release, Development Timeline. 기획 단계(WIP)부터 출시 후까지 등록 가능.
- **[제안]** Release 시스템: v0.1 → Beta → v1.0 → v1.1 성장 과정을 한 페이지에 축적(Relaunch 개념).
- **[제안]** 재노출: 개발로그나 Release를 올리면 프로젝트가 피드/Discovery에 다시 등장. 흐름: 개발로그 작성 → 팔로워 피드 → "최신 개발 중 프로젝트" → 프로젝트 상세 유입.
- **[제안]** 한국 개발자 중심 태그(앱인토스, Flutter, Expo, Supabase, 카카오API, 네이버API 등).

### 4.5 공식·자동 콘텐츠 (3층)

- **[결정]** 활성화율이 낮고 게시물이 적어도 죽어 보이면 안 된다. 초기에는 공식 피드가 튜토리얼처럼 유저 피드를 대신한다. 자동화 카드뉴스 파이프라인을 만든다.
- **[제안]** 2층 피드: Community Feed(실제 게시물) + Official Feed(튜토리얼·챌린지·추천·샘플). 공식 게시물은 "우리 서비스 이용하세요" 광고 반복이 아니라 실제 콘텐츠여야 한다.
- **[제안]** 공식 콘텐츠 종류: 개발로그 작성 가이드(좋은 예/나쁜 예) / 오늘의 Build Prompt(매일 자동 교체) / Weekly Challenge(#BeforeAfter 등) / Demo Project("Demo Project"라고 명시, 인터랙티브 튜토리얼 역할) / **서비스 자체 devlog**(빌드로그를 빌드로그 안에서 공식 프로젝트로 연재) / 비게시물 UI 블록(지금 개발 중, 이번 주 많이 쓰인 Stack).
- **[제안]** 자동 카드뉴스 종류와 MVP 우선순위: Build Prompt ★5, Project Spotlight ★5(사용자 프로젝트를 공식 콘텐츠로 재생산) — 둘은 외부 의존 없어 최우선 / 개발 Tip ★5 / Tech Release ★4 / Weekly Digest ★4 / 개발 뉴스.
- **[제안]** 파이프라인: 소스 → 수집 → 중복·품질 필터 → 요약 → 카드뉴스 원고 → 템플릿 선택 → 이미지 렌더링 → 검수 → 예약 게시 → 피드 노출. 소스는 크롤링 대신 공식 블로그(Flutter, React, Supabase), GitHub Trending/Release, RSS, 서비스 자체 DB(새 프로젝트·Release), 운영자 작성, 자동 생성(Build Prompt).
- **[제안]** 데이터는 이미지가 아니라 JSON(type, title, summary, source{name,url}, slides[{type: cover|bullet, …}])으로 저장 → React 카드 컴포넌트로 렌더. 사이트에서는 컴포넌트 그대로 피드 카드로 표시하고 공유 시에만 PNG/WebP 생성. 1장보다 3~5장 캐러셀. 디자인이 바뀌면 전체 재렌더링.
- **[제안]** 자동화 단계: 1단계(과제 버전) 수집 → AI 원고 → Preview → 관리자 승인 → 게시(반자동) / 2단계 신뢰 가능한 유형 자동 게시 / 3단계 조회·저장·클릭 성과를 다음 주제 선정에 반영. 관리자 Content Pipeline 대시보드(수집됨/생성 대기/검수 필요/예약 게시, 미리보기·수정·승인·예약·삭제).

### 4.6 피드·탐색

- **[제안]** 스팸 방지: "글 많이 쓰면 무조건 상위"가 아니라 활동 점수 = 최근 7일 개발로그 + 실제 Release 등록 + 이미지/GIF 포함 + 다른 사용자 반응 + 프로젝트 정보 완성도. 로그 하나당 Boost 1회, 주 최대 2회.
- **[제안]** 피드 타입 5: Dev Log / Project Update(새 버전·출시) / Build Prompt / Official Guide / Discovery Card(다른 프로젝트 추천). 가끔 Challenge·Stack Trend·Release·Featured.
- **[제안]** 메인 섹션: 지금 뜨는 프로젝트 / 이번 주 개발 중 / 오늘 출시 / 최근 업데이트 / 카테고리(모바일 앱, 인디 게임, AI, 개발자 도구, 웹 서비스). 탐색: 태그·검색·최신·인기.
- **[제안]** 개인화 비율: 신규 Official 70% · Discovery 30% → 팔로우 시작 Official 40% · User 60% → 활발 Official 10% · Following 60% · Discovery 30%.
- **[제안]** 더미 데이터 원칙: 제품·제작자·스크린샷·Demo·태그·스택은 채우되 가짜 Upvote·가짜 댓글·가짜 사용자 활동은 넣지 않는다(가짜 커뮤니티로 보일 위험).

### 4.7 프로필·소셜·수익화

- **[제안]** 개발자/팀 프로필이 여러 프로젝트를 소유하고 개발로그를 포트폴리오처럼 축적. 위치는 회사/팀 위치·지역·지도(개인은 선택). 구현 예: 주소 검색 → 좌표 저장, Kakao Map/Google Map 표시, "서울/부산/경기" 지역 표시.
- **[제안]** 팔로우 대상: 개발자 또는 프로젝트. MVP 소셜 범위: 좋아요 / 저장 / 팔로우(댓글은 매핑표에만 있고 MVP 표에는 없음). 알림·리뷰는 언급 없음.
- **[제안]** 유료 상품: 프로젝트 Featured(3일·7일), 게시물 Boost, Release Spotlight. 흐름: 프로젝트 선택 → 홍보 상품 선택 → 결제 → 일정 기간 추가 노출. 과제의 결제·취소·내역을 모두 덮는다. 취소: 노출 시작 전이면 취소 가능 같은 단순 규칙. 리서치에 나온 가격(₩2,900~9,900)은 참고 예시일 뿐 확정이 아니므로 문서에 쓰지 않는다. 후원 모델은 철회.

### 4.8 MVP 표·기술·문서 운영

- **[제안]** MVP: 회원(가입/로그인/프로필) / 프로젝트 CRUD / 피드 CRUD / 미디어(이미지·GIF) / 외부 콘텐츠(YouTube·GitHub·URL Preview) / 게시물↔프로젝트 연결 / 소셜(좋아요·저장·팔로우) / 탐색(태그·검색·최신·인기) / Release / 홍보(Featured·Boost) / 결제(결제·취소·내역) / 위치(개발자 또는 팀) / 운영(공식 피드·콘텐츠 관리). 자동화는 1단계 반자동부터.
- **[제안]** 스택(초기 맥락에서 제시, 빌드로그 기준 재검토 필요): Next.js, TypeScript, Tailwind CSS, Supabase(PostgreSQL·Auth·Storage·RLS), Kakao Maps API, Toss Payments(테스트 결제, v2), Vercel, 선택적으로 Cloudflare. 사용자 배경: 앱 개발, Supabase, 서버/배포, Expo, Cloudflare 경험.
- **[결정]** 문서 운영: 기획서 각 페이지에 ASCII 와이어프레임을 먼저 두고 구조를 굳힌 뒤, 정리되면 Codex로 넘겨 상세 기획을 만든다. 초기에 이미지 디자인에 들어가지 않는다.
- **[결정]** 소개 사이트는 실제 서비스와 분리("배달의민족 홈페이지"처럼 홍보용). 소개 사이트에 CRUD·SNS 기능을 넣지 않는다. (완료)
- **[보류]** 실제 서비스 상세 기획서와 40일 로드맵은 미작성. 대화에 남은 40일 예시(1~7일 랜딩·가입·DB / 8~14 CRUD / 15~20 검색·업로드 / 21~25 지도 / 26~31 예약 / 32~35 Toss 결제 / 36~40 관리자·배포)는 이전 아이디어용이라 그대로 쓰지 않는다.
- 이름: 이 대화에서는 이름이 정해지지 않았다("BuildLog"는 후보 표와 가정 예시로만 등장). 빌드로그 확정은 2026-09-16 별도 결정(1절).

## 5. 열린 질문 (기획하면서 결정하거나 사용자에게 물을 것)

기획 문서를 쓰기 전에 사용자에게 한 번에 묶어서 물어보는 편이 낫다. 질문은 한국어로. 4절의 **[제안]**을 그대로 채택할지 묻는 형태가 빠르다.

1. **MVP 범위:** 4.8의 MVP 표를 그대로 갈지, 40일 안에서 무엇을 뒤로 미룰지(자동 카드뉴스 파이프라인의 범위, Featured/Boost, 위치).
2. **팔로우 단위:** 개발자 팔로우인가, 프로젝트 팔로우(구독)인가, 둘 다인가.
3. **댓글:** MVP에 넣는가(ChatGPT 매핑표에는 있고 MVP 표에는 없음). 알림은 어디까지.
4. **숫자 노출:** 좋아요·팔로워·조회 수를 화면에 보이는가. 소개 사이트는 의도적으로 숫자를 뺐고, 더미 데이터 원칙은 가짜 반응 숫자를 금지한다.
5. **피드 정렬:** 최신순 + 재노출인가, 4.6의 활동 점수·Boost 제한(로그당 1회, 주 2회)·개인화 비율을 채택하는가.
6. **Release:** 등록 UI(별도 액션)와 버전 규칙(v0.1 → Beta → v1.0), 타임라인 항목의 편집·삭제 허용 범위.
7. **공식 카드 운영:** 1단계 반자동(관리자 승인)으로 시작하는가. 소스 목록, 요약 모델, 출처 표기 규칙. Demo Project 개수, 서비스 자체 devlog 연재 주기.
8. **인증·계정:** 소셜 로그인(GitHub·Google)·이메일 중 무엇. 팀 계정(여러 사람이 한 프로젝트 관리)을 MVP에 넣는가.
9. **미디어·외부 연동:** 이미지·GIF 용량과 저장소(Supabase Storage?), 유튜브·GitHub·앱스토어·웹사이트 미리보기 방식(oEmbed/OG 파싱).
10. **결제:** Toss Payments 테스트 결제로 Featured·Boost·Release Spotlight 중 무엇을 먼저. 노출 기간·취소 조건. 가격은 미정이므로 문서에 숫자를 쓰지 않는다.
11. **위치:** 필수인가 선택인가, Kakao Map인가 Google Map인가, 프로필에만 두는가.
12. **플랫폼·스택:** 웹 우선(Next.js + Supabase + Vercel 제안)으로 가는가, 모바일 앱은 언제. 4.8 스택을 빌드로그 기준으로 재확인.
13. **모더레이션·신고:** 개발 프로젝트가 아닌 게시물·스팸 처리 방침.
14. **도메인·표기:** 서비스 도메인 미정. 영문 BuildLog와 한글 빌드로그 병기 방식.

## 7. 지켜야 할 규칙

- 화면 문구는 현재형·존댓말("~합니다"). 구체어(게시물·스크린샷·피드·프로젝트 페이지·유튜브 링크)를 쓰고 추상어(기록·이야기·발견)를 남발하지 않는다.
- 다른 서비스의 이름·로고·색·아이콘을 쓰지 않는다. 문구에서 다른 서비스와 비교하지 않는다.
- 가짜 숫자·후기·가격을 쓰지 않는다. 데모 콘텐츠는 데모라고 표시한다.
- 서비스 이름은 상수 한 곳에서 관리한다(소개 사이트는 `app/site.ts`의 `SERVICE`). 한글 조사: 빌드로그는/를/가.
- 문서 형식은 소개 사이트 `docs/`를 따라도 된다: 01 제품 기획(정의·타깃·구조·FR·BR·완료 기준·변경 이력), 02 기술 명세, 03 현황(검증 표: PASS/FAIL/INCOMPLETE/NOT_RUN/UNKNOWN + 근거·날짜·리비전), 04 작업 흐름, README.

## 8. Codex에게 요청하는 산출물

1. `docs/01_PRODUCT_SPEC.md` — 실제 서비스 제품 기획: 정의, 타깃, 3층 구조, 화면 목록(피드·올리기·프로젝트 페이지·프로필·탐색/검색·알림·설정·결제·관리자 콘텐츠 파이프라인)과 **페이지별 ASCII 와이어프레임**(사용자 결정: 이미지 디자인보다 먼저), 기능 요구사항(FR), 규칙(BR), MVP 범위와 이후 단계, 완료 기준.
2. `docs/02_TECH_SPEC.md` — 스택 제안(근거 포함), 데이터 모델(개발자·팀·프로젝트·게시물(타입별)·릴리스·공식 카드(JSON 슬라이드)·좋아요/저장/팔로우·결제·위치), 외부 연동(유튜브·GitHub·앱스토어·OG 미리보기), 미디어 저장, 인증, 결제(Toss), 지도, 배포.
3. `docs/03_PROJECT_STATUS.md` — 비어 있는 검증 표와 첫 인수인계.
4. **40일 로드맵** — 과제 조건(로그인, CRUD, 지도, 결제·취소·내역, 점진 업그레이드)을 모두 덮되, 4.1의 순서와 4.8 MVP 표를 기준으로 빌드로그에 맞게 새로 짠다. 대화 속 예전 40일 예시는 쓰지 않는다.
5. 사용자에게 물을 질문 목록(5절 기준으로 다듬어서, 한국어로, 한 번에).
6. 결정 이유가 필요한 것만 `docs/decisions/ADR-xxx.md`.

먼저 5절 질문에 대한 답을 받은 뒤 1~4를 쓰는 순서를 권한다. 답을 못 받으면 **[추정]**으로 표시하고 진행한다.
